**Event loop** (цикл подій) — це механізм, який вирішує, що JavaScript виконає наступним. Сам JavaScript виконує код в одному потоці: один рядок за раз, на одному **стеку викликів**. Таймери, мережа й події працюють поза ним, а їхні колбеки стають у черги. Цикл подій чекає, поки стек звільниться, і бере з черг наступну роботу за чіткими правилами.

Головне правило вміщується в один рядок: **синхронний код → усі мікрозадачі → (рендеринг) → одна макрозадача → знову всі мікрозадачі**. Саме тому `Promise.then` спрацьовує раніше за `setTimeout(..., 0)`, навіть якщо таймер стоїть у коді вище. Мікрозадачі — це обробники промісів, продовження після `await` і `queueMicrotask`. Макрозадачі — колбеки таймерів, події, повідомлення.

Навіщо це знати? Без event loop не зрозуміти, чому інтерфейс «зависає» від важкого циклу, чому лічильник у `setTimeout` показує не те число і як упорядкувати асинхронний код. А на співбесідах Junior і Middle задача «що виведе цей код» з `setTimeout`, `then` і `await` трапляється майже завжди. Нижче — механізм по кроках, розбір типових задач, рендеринг і особливості Node.js. Увесь код перевірено в Node.js 25 (файли `.mjs`, тобто ES-модулі) і можна запустити в консолі браузера.

## Стек викликів: JavaScript робить одну справу за раз

**Стек викликів** (call stack) — це список функцій, які виконуються просто зараз. Викликали функцію — вона кладеться на верх стека. Функція повернула результат — знімається. Стек працює за принципом «останнім прийшов — першим вийшов», як стос тарілок.

```js
function square(x) {
  return x * x;
}

function printSquare(x) {
  const result = square(x); // стек: printSquare → square
  console.log(result);      // стек: printSquare → console.log
}

printSquare(4); // 16
// після повернення printSquare стек знову порожній
```

Поки на стеку щось є, нічого іншого JavaScript не робить. У [документації MDN про модель виконання](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model) це називається **run-to-completion**: кожна задача виконується до кінця, і лише потім починається наступна. Ніхто не перерве твою функцію посередині, щоб виконати колбек таймера.

Звідки тоді асинхронність? Таймер відлічує браузер (або Node.js), мережевий запит виконує мережевий стек, кліки ловить операційна система. Це робота **середовища**, а не рушія JavaScript. Коли таймер спрацював чи відповідь прийшла, середовище не втручається в стек, а ставить колбек у **чергу**. Далі все вирішує цикл подій.

Перевіримо, що буде, якщо зайняти стек на секунду:

```js
const start = Date.now();
setTimeout(() => console.log(`таймер спрацював через ${Date.now() - start} мс`), 0);

while (Date.now() - start < 1000) {} // зайнятий стек на 1 секунду
console.log('цикл завершився');

// цикл завершився
// таймер спрацював через 1004 мс
```

Час таймера на 0 мс настав майже одразу, але колбек простояв у черзі цілу секунду: стек був зайнятий. Число в тебе може трохи відрізнятися, але точно буде не менше 1000.

## Черга задач і черга мікрозадач

Черг насправді дві, і пріоритет у них різний. У стандарті HTML їх називають **tasks** і **microtasks**; у статтях і на співбесідах кажуть «макрозадачі» й «мікрозадачі».

| | Макрозадачі (tasks) | Мікрозадачі (microtasks) |
|---|---|---|
| Що туди потрапляє | колбеки `setTimeout`, `setInterval`, події (клік, введення), `MessageChannel`, запуск `<script>` | обробники `then`, `catch`, `finally`, продовження після `await`, `queueMicrotask`, `MutationObserver` |
| Скільки за один оберт | одна, найстаріша | усі, поки черга не спорожніє |
| Чи можна «перескочити» чергу | ні | так: мікрозадача, додана з мікрозадачі, виконається в тому ж обороті |
| Типове призначення | реакція на зовнішні події й таймери | «доробити одразу після поточного коду» |

[Гайд MDN про мікрозадачі](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide) формулює ключову різницю так: мікрозадача виконується після того, як завершився код, що її створив, і лише коли стек порожній, але ще до того, як керування повернеться циклу подій. А цикл подій викликає мікрозадачі, доки вони не закінчаться, навіть якщо нові весь час додаються.

![Цикл подій: стек викликів, черга мікрозадач і черга макрозадач](/blog/event-loop-javascript-prostymy-slovamy/img-1.webp)

Найкоротший приклад, який показує обидві черги:

```js
console.log('1: старт');
setTimeout(() => console.log('2: setTimeout'), 0);
Promise.resolve().then(() => console.log('3: then'));
queueMicrotask(() => console.log('4: queueMicrotask'));
console.log('5: кінець');

// 1: старт
// 5: кінець
// 3: then
// 4: queueMicrotask
// 2: setTimeout
```

Спершу весь синхронний код (1 і 5). Стек порожній — виконуються мікрозадачі в порядку постановки (3, 4). Лише потім цикл бере макрозадачу — колбек таймера (2).

> [!note] Нотатка
> Event loop не описаний у специфікації мови ECMAScript. Цикл подій браузера визначає [стандарт HTML](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops), а в Node.js свій цикл на основі бібліотеки libuv. Тому поведінка в браузері й у Node.js збігається в головному, але відрізняється в деталях.

## Один оберт циклу подій крок за кроком

Спростимо алгоритм зі стандарту до п'яти кроків, яких вистачить для будь-якої задачі зі співбесіди:

1. Виконати весь синхронний код скрипта, поки стек не спорожніє. Сам скрипт — теж задача.
2. Виконати **всі** мікрозадачі. Якщо під час цього з'являються нові, виконати й їх.
3. Браузер може оновити сторінку: перерахувати стилі, макет і намалювати кадр. Перед малюванням викликаються колбеки `requestAnimationFrame`.
4. Взяти з черги **одну** макрозадачу (найстарішу готову) і виконати її.
5. Повернутися до кроку 2.

![Один оберт циклу: синхронний код, усі мікрозадачі, рендеринг, одна макрозадача](/blog/event-loop-javascript-prostymy-slovamy/img-2.webp)

Звідси два наслідки, які варто запам'ятати.

**Мікрозадачі можуть «загнати» цикл.** Якщо мікрозадача щоразу ставить нову, цикл так і не дійде ні до таймерів, ні до рендерингу. MDN прямо попереджає про ризик нескінченної обробки мікрозадач:

```js
let done = 0;
function tick(n) {
  if (n === 0) return;
  done++;
  queueMicrotask(() => tick(n - 1)); // мікрозадача ставить нову мікрозадачу
}

setTimeout(() => console.log('таймер; мікрозадач уже виконано:', done), 0);
tick(100_000);

// таймер; мікрозадач уже виконано: 100000
```

Таймер чекав, поки пройдуть усі сто тисяч мікрозадач. Зроби ланцюжок нескінченним — і сторінка зависне так само, як від `while (true)`.

**Макрозадачі по одній, а між ними — мікрозадачі.** Якщо в колбеку таймера створити проміс, його `then` виконається до наступного таймера, навіть якщо той уже давно в черзі.

## Розбираємо задачі зі співбесід

Метод для будь-якої такої задачі однаковий: пройди код зверху вниз і випиши три колонки — «вивід зараз», «мікрозадачі», «макрозадачі». Потім спорожни мікрозадачі, візьми одну макрозадачу, знову мікрозадачі й так далі.

### Задача 1: таймери всередині промісів і навпаки

```js
console.log('A');
setTimeout(() => {
  console.log('B');
  Promise.resolve().then(() => console.log('C'));
}, 0);
setTimeout(() => console.log('D'), 0);
Promise.resolve().then(() => {
  console.log('E');
  setTimeout(() => console.log('F'), 0);
});
console.log('G');

// A
// G
// E
// B
// C
// D
// F
```

Розбір:

| Крок | Вивід | Мікрозадачі | Макрозадачі |
|---|---|---|---|
| синхронний код | A, G | then(E) | таймер B, таймер D |
| мікрозадачі | E | — | B, D, F |
| макрозадача B | B | then(C) | D, F |
| мікрозадачі | C | — | D, F |
| макрозадача D | D | — | F |
| макрозадача F | F | — | — |

Пастка тут у `C`: він виводиться раніше за `D`, хоча таймер `D` поставили набагато раніше, ніж проміс `C`. Після кожної макрозадачі цикл спершу спорожнює мікрозадачі.

### Задача 2: async-функція й await

```js
async function load() {
  console.log('2: load почалася');
  await null;
  console.log('4: після await');
}

console.log('1: старт');
setTimeout(() => console.log('6: setTimeout'), 0);
load();
Promise.resolve().then(() => console.log('5: then'));
console.log('3: кінець');

// 1: старт
// 2: load почалася
// 3: кінець
// 4: після await
// 5: then
// 6: setTimeout
```

Тіло async-функції до першого `await` виконується **синхронно**, просто під час виклику. Усе, що після `await`, — мікрозадача. Вона потрапила в чергу раніше за `then` (бо `load()` викликали вище), тому й виконалася першою. Докладно про те, як працюють проміси й `await`, — у статті [Promise і async/await у JavaScript](/blog/promise-async-await-javascript).

### Задача 3: var у циклі з setTimeout

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var:', i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log('let:', j), 0);
}

// var: 3
// var: 3
// var: 3
// let: 0
// let: 1
// let: 2
```

Тут event loop пояснює лише половину: колбеки виконуються **після** того, як цикл завершився, бо цикл — синхронний код. З `var` змінна одна на всю функцію, і на момент виклику там уже 3. З `let` кожна ітерація отримує власну змінну, яку запам'ятовує колбек. Другу половину пояснення дають [замикання в JavaScript](/blog/zamykannia-v-javascript-prostymy-slovamy).

## Рендеринг, requestAnimationFrame і довгі задачі

У браузері той самий потік, що виконує твій JavaScript, ще й малює сторінку. Тому поки на стеку важке обчислення, кнопки не натискаються, анімації стоять, а текст у полі не з'являється. Браузер просто не дістається до кроку рендерингу. MDN радить робити задачі короткими й розбивати великі на частини.

Розбити роботу на порції можна, віддаючи керування циклу подій між ними:

```js
// Обробка великого масиву порціями, щоб не блокувати потік
const items = Array.from({ length: 1_000_000 }, (_, i) => i);
let sum = 0;
let i = 0;

const yieldToLoop = () => new Promise((resolve) => setTimeout(resolve, 0));

async function processAll() {
  while (i < items.length) {
    const end = Math.min(i + 100_000, items.length);
    for (; i < end; i++) sum += items[i];
    await yieldToLoop(); // віддаємо керування циклу подій
  }
  console.log('сума:', sum);
}

processAll();
setTimeout(() => console.log('інший колбек встиг виконатися'), 0);

// інший колбек встиг виконатися
// сума: 499999500000
```

Зверни увагу: пауза зроблена через `setTimeout`, тобто через **макрозадачу**. Якби там було `await Promise.resolve()`, продовження стало б мікрозадачею, і браузер так само не встиг би ні намалювати кадр, ні обробити клік. Мікрозадачі не дають циклу «перепочити».

Для анімацій є окремий інструмент — [`requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame). Його колбек браузер викликає перед наступним перемальовуванням, зазвичай із частотою оновлення екрана. Це точніше, ніж `setTimeout(draw, 16)`: кадр не пропуститься й не намалюється двічі.

> [!warning] Увага
> Затримка в `setTimeout` — це мінімум, а не гарантія. За [MDN про setTimeout](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout), після п'яти вкладених викликів браузери ставлять мінімальну затримку 4 мс, у неактивних вкладках таймери пригальмовуються (у Firefox Desktop — щонайменше до 1 секунди), а затримка понад 2 147 483 647 мс (близько 24,8 доби) переповнюється. Для точного відліку часу таймерам не довіряй.

## Event loop у Node.js: фази, nextTick і setImmediate

Node.js теж виконує JavaScript в одному потоці, але цикл подій там інший — на основі libuv. За [офіційним гайдом Node.js](https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick), кожен оберт проходить фази в такому порядку:

| Фаза | Що виконується |
|---|---|
| timers | колбеки `setTimeout` і `setInterval`, час яких настав |
| pending callbacks | деякі колбеки введення-виведення, відкладені з попереднього оберту |
| idle, prepare | лише для внутрішніх потреб |
| poll | нові події введення-виведення та їхні колбеки; тут Node.js може чекати |
| check | колбеки `setImmediate` |
| close callbacks | колбеки закриття, як-от `socket.on('close')` |

Між колбеками виконуються дві «позачергові» черги: спершу черга `process.nextTick`, потім мікрозадачі промісів. Але з одним нюансом, про який мало хто знає. За [документацією модуля process](https://nodejs.org/api/process.html#when-to-use-queuemicrotask-vs-processnexttick), у CommonJS `nextTick` іде перед промісами, а в ES-модулях навпаки: код модуля вже виконується всередині черги мікрозадач, тому `then` і `queueMicrotask` спрацьовують першими.

```js
// файл order.cjs (CommonJS)
const fs = require('node:fs');

console.log('1: синхронно');
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('2: nextTick'));
Promise.resolve().then(() => console.log('3: then'));

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout у колбеку I/O'), 0);
  setImmediate(() => console.log('immediate у колбеку I/O'));
});

// 1: синхронно
// 2: nextTick
// 3: then
// timeout          ← ці два рядки можуть
// immediate        ← помінятися місцями
// immediate у колбеку I/O
// timeout у колбеку I/O
```

У головному модулі порядок `setTimeout(..., 0)` і `setImmediate` **не визначений**: він залежить від того, як швидко процес дійде до фази timers. Ми запустили цей файл п'ять разів, і один раз `immediate` вийшов першим. А всередині колбеку введення-виведення порядок завжди однаковий: після фази poll іде check, тому `setImmediate` випереджає таймер.

> [!tip] Порада
> Документація Node.js позначає `process.nextTick` як застарілий (legacy) і радить у звичайному коді використовувати `queueMicrotask`: він працює однаково в браузері й Node.js. Рекурсивні виклики `nextTick` ще й можуть «заморити голодом» введення-виведення: цикл не дійде до фази poll.

## Типові помилки

**1. «setTimeout з нулем виконується одразу».** Ні: колбек стає в чергу макрозадач і чекає, поки виконається весь синхронний код і всі мікрозадачі. Нуль — це «не раніше ніж зараз», а не «зараз».

**2. Думати, що await блокує весь JavaScript.** `await` призупиняє лише поточну async-функцію, решта коду працює далі. А от синхронний цикл на мільйон ітерацій справді блокує все, і жоден `async` перед функцією цього не змінить.

**3. Вважати, що код після async-виклику виконається раніше за тіло функції.** Тіло async-функції до першого `await` виконується синхронно, у момент виклику. Асинхронним стає лише те, що після `await`.

**4. Розбивати важку роботу через `await Promise.resolve()`.** Продовження буде мікрозадачею, і браузер так і не отримає шансу намалювати кадр чи обробити клік. Щоб «відпустити» потік, потрібна макрозадача: `setTimeout`, `MessageChannel` або `requestAnimationFrame` для анімацій.

**5. Забувати, що мікрозадачі з мікрозадач теж виконуються одразу.** Ланцюжок `then` або рекурсивний `queueMicrotask` виконається повністю до наступного таймера. Нескінченний ланцюжок вішає сторінку.

**6. Покладатися на порядок `setTimeout(0)` і `setImmediate` у Node.js.** У головному модулі він випадковий. Якщо порядок важливий, вибудовуй залежність явно: проміси, колбеки, `await`.

**7. Плутати середовища.** Відповідь «nextTick завжди перед then» правильна для CommonJS, але не для ES-модулів. На співбесіді варто уточнити, про яке середовище питають.

## Перевір себе

1. Що виведе код?
   ```js
   setTimeout(() => console.log('1'), 0);
   Promise.resolve()
     .then(() => console.log('2'))
     .then(() => console.log('3'));
   queueMicrotask(() => console.log('4'));
   console.log('5');
   ```
2. Що виведе код?
   ```js
   async function f() {
     console.log('a');
     await Promise.resolve();
     console.log('b');
   }
   setTimeout(() => console.log('c'), 0);
   f();
   console.log('d');
   ```
3. У якому порядку спрацюють таймери?
   ```js
   setTimeout(() => console.log('x'), 10);
   setTimeout(() => console.log('y'), 0);
   Promise.resolve().then(() => setTimeout(() => console.log('z'), 0));
   ```
4. Кнопка запускає обчислення, яке триває 3 секунди. Весь цей час сторінка не реагує. Чому, і що з цим зробити?
5. Чи допоможе `await Promise.resolve()` усередині важкого циклу, щоб браузер встигав малювати кадри?

> [!solution]- Відповіді
> 1. `5 2 4 3 1`. Синхронно виводиться `5`. На старті в черзі мікрозадач два обробники: `then` з `2` і `queueMicrotask` з `4`. Обробник із `3` стає в чергу лише після того, як виконався `2`, тому йде після `4`. Останнім — таймер `1`.
> 2. `a d b c`. Тіло `f` до `await` синхронне (`a`), далі синхронне `d`, потім мікрозадача-продовження (`b`), і лише тоді макрозадача (`c`).
> 3. `y z x`. Таймер `z` ставиться з мікрозадачі майже одразу з нульовою затримкою, тож він готовий раніше, ніж таймер `x` на 10 мс.
> 4. Обчислення займає стек викликів, і цикл подій не доходить ні до обробки подій, ні до рендерингу. Варіанти: розбити роботу на порції з паузами через `setTimeout`, перенести обчислення у Web Worker (окремий потік) або оптимізувати сам алгоритм.
> 5. Ні. Продовження після такого `await` — мікрозадача, а всі мікрозадачі виконуються до рендерингу. Потрібна макрозадача, наприклад `await new Promise((r) => setTimeout(r, 0))`.

## Коротко

- JavaScript виконує код в одному потоці на стеку викликів; кожна задача виконується до кінця, і ніхто її не перериває.
- Таймери, мережу й події обслуговує середовище, а колбеки ставить у черги. Event loop бере їх, коли стек порожній.
- Порядок: синхронний код → усі мікрозадачі → рендеринг → одна макрозадача → знову всі мікрозадачі.
- Мікрозадачі — `then`, `catch`, `finally`, продовження після `await`, `queueMicrotask`. Макрозадачі — `setTimeout`, `setInterval`, події.
- Довгий синхронний код і нескінченні мікрозадачі блокують сторінку; важку роботу розбивай на порції з макрозадачами або виноси у Web Worker.
- У Node.js цикл має фази (timers, poll, check…), `setImmediate` спрацьовує у фазі check, а порядок `nextTick` і промісів залежить від того, CommonJS у тебе чи ES-модулі.

Якщо тільки вибудовуєш порядок тем, глянь [план вивчення JavaScript з нуля](/blog/javascript-z-nulya): event loop логічно йде після функцій, замикань і промісів. А потренувати задачі «що виведе код» можна в курсі [JavaScript Zero→Pro на Loo](https://playloo.app).
