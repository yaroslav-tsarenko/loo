# Вступний тест — банк god

Калібрований банк питань рівня **god** для вступного тесту курсу «Next.js Zero → Pro». Це не стаття: компілятор
додає ці питання лише до вступного тесту. Рівень бере назва файлу (`god.md`), тож у рядку мета його немає. `diff`:
1 — легке для рівня, 2 — типове, 3 — найскладніше. Орієнтир рівня: архітектура великих систем, платформні нюанси PPR,
prefetch і CDN, компроміси між швидкістю, вартістю й безпекою. Базова конфігурація — `cacheComponents: true`.

## foundations

> [!quiz] Origin віддає `/pricing` різними мовами за `Accept-Language` і ставить `Vary: Accept-Language`. CDN ігнорує `Vary` і кешує за URL. Що станеться?
> skill: foundations · diff: 1 · id: nextjs-pl-foundations-god-01
> - [ ] CDN сам розбере `Accept-Language` і збереже по копії на кожну мову
> - [ ] CDN перестане кешувати сторінку взагалі
> - [x] Усі отримають мову першого закешованого запиту
> - [ ] Браузер виправить мову після завантаження за `navigator.language`
>
> **Пояснення:** `Vary` — єдиний сигнал, що відповідь залежить від заголовка запиту; CDN, який його ігнорує, тримає одну копію на URL. Тому мову, варіант A/B чи тип відповіді надійніше кодувати в URL — так само Next.js додає `_rsc` до RSC-запитів, щоб не залежати від підтримки `Vary`.

> [!quiz] Чому в Server Component не можна викликати `(await cookies()).set(...)`, а в Server Action чи Route Handler — можна?
> skill: foundations · diff: 2 · id: nextjs-pl-foundations-god-02
> - [x] Після початку стріму заголовки вже відправлені
> - [ ] Server Components виконуються на build-сервері без доступу до відповіді
> - [ ] cookies доступні для запису лише в Edge runtime, а рендер іде в Node.js
> - [ ] Це обмеження безпеки
>
> **Пояснення:** документація `cookies()` пояснює саме так: HTTP не дозволяє ставити cookies після початку стріму. Server Action і Route Handler формують відповідь цілком до відправки, тож заголовки ще можна змінити. Той самий контракт пояснює `200` + `noindex` для `notFound()` посеред стріму.

> [!quiz] Під час переходу на вкладку, що суспендиться, користувач бачить старий вміст з індикатором, а не fallback `<Suspense>`. Чому?
> skill: foundations · diff: 2 · id: nextjs-pl-foundations-god-03
> - [x] Перехід іде як Transition: React не ховає вже показаний вміст
> - [ ] Fallback показується лише при першому рендері сторінки, далі React його вимикає
> - [ ] Браузер тримає попередній DOM, поки не прийде новий HTML документа
> - [ ] `<Suspense>` працює лише на сервері, а на клієнті fallback не рендериться
>
> **Пояснення:** термінові оновлення можуть одразу показати fallback, а Transition — ні для меж, що вже показали вміст: це запобігає «миготінню» скелетонів. Тому `useLinkStatus` чи `isPending` з `useTransition` — спосіб показати очікування. Fallback новонамонтованої межі React однаково покаже.

> [!quiz] Мобільний клієнт повторює `POST /payments` після таймауту мережі, і частина клієнтів платить двічі. Яке архітектурне рішення?
> skill: foundations · diff: 2 · id: nextjs-pl-foundations-god-04
> - [ ] Замінити `POST` на `GET`: він ідемпотентний, тож повтор безпечний
> - [ ] Відповідати `307`, щоб клієнт не повторював запит після таймауту
> - [ ] Збільшити таймаут клієнта
> - [x] `Idempotency-Key` і збережений результат
>
> **Пояснення:** `POST` не ідемпотентний за визначенням, а мережа не гарантує, що клієнт дізнається про успіх. Ключ ідемпотентності перетворює «повтори» на безпечну операцію: сервер розпізнає той самий намір. `GET` для зміни стану — помилка (prefetch і боти його викличуть), а більший таймаут лише зменшить імовірність.

> [!quiz] `getUser(orderId)` скомпілювався, хоча прийняв id замовлення замість id користувача. Обидва — `string`. Що запобіжить цьому класу помилок на рівні типів?
> skill: foundations · diff: 2 · id: nextjs-pl-foundations-god-05
> - [ ] `interface UserId extends String {}` — окремий інтерфейс робить тип несумісним
> - [ ] `type UserId = string` — псевдонім робить тип окремим від інших рядків
> - [ ] `enum UserId` з усіма можливими id
> - [x] Branded type з функцією-валідатором
>
> **Пояснення:** TypeScript структурний: псевдонім `string` лишається `string`, і будь-які два рядки сумісні. «Бренд» — фантомне поле, якого немає в рантаймі, але яке робить типи несумісними; значення отримують через `parseUserId()`, що перевіряє формат. Приклад: id з `params`, які перевірено один раз на межі.

> [!quiz] Client Component створює promise під час рендеру і читає його через `use()`. Компонент нескінченно показує fallback або сипле попередженнями. Чому?
> skill: foundations · diff: 3 · id: nextjs-pl-foundations-god-06
>
> ```tsx
> 'use client'
> import { use } from 'react'
>
> export function Stats() {
>   const stats = use(fetch('/api/stats').then((r) => r.json()))
>   return <p>{stats.total}</p>
> }
> ```
>
> - [ ] `use` не працює з `fetch`, лише з контекстом і серверними даними
> - [ ] Бракує `await` перед `fetch`
> - [ ] `use` можна викликати лише в Server Components, у клієнті він зависає
> - [x] Кожен рендер створює новий promise
>
> **Пояснення:** `use(promise)` чекає на **той самий** promise між рендерами. Promise треба створити поза рендером — у Server Component і передати пропом (так стрімлять дані в клієнт), закешувати або взяти бібліотеку на кшталт TanStack Query. React прямо попереджає про promise, створені в Client Component без кешу.

## routing

> [!quiz] Свій CDN перед Next.js не пересилає заголовок `rsc` на origin. Що побачать користувачі?
> skill: routing · diff: 1 · id: nextjs-pl-routing-god-01
> - [ ] Нічого: `rsc` — лише налагоджувальна мітка для DevTools
> - [ ] Повільніші prefetch-і, але клієнтська навігація працюватиме як раніше
> - [x] Переходи стануть повними завантаженнями
> - [ ] `401` на кожну клієнтську навігацію
>
> **Пояснення:** заголовок `rsc` каже серверу віддати payload замість HTML. Без нього роутер отримує не те, що очікує, і переходить жорстко — документація CDN caching називає `rsc` обовʼязковим для пересилання. Можна безпечно опустити `next-router-state-tree` (прийде повний payload замість точкового), але не `rsc`.

> [!quiz] Після міграції на новий CDN модалки на intercepting routes перестали відкриватися: клік по фото в стрічці веде на повну сторінку фото. Що CDN, найімовірніше, зрізає?
> skill: routing · diff: 2 · id: nextjs-pl-routing-god-02
> - [ ] `next-router-prefetch`, тож модалку перестали prefetch-ити
> - [ ] `x-nextjs-stale-time`, і перехоплена сторінка вважається протухлою
> - [ ] Query-параметр `_rsc` з кешового ключа, і CDN віддає HTML
> - [x] `next-url`
>
> **Пояснення:** `next-url` додається лише для маршрутів з перехопленням і несе адресу, з якої йде навігація. Документація: якщо його немає, interception не підтримується, і користувач бачить цільову сторінку замість перехопленої. Без `_rsc` у ключі ризик інший — змішати HTML- і RSC-варіанти.

> [!quiz] Платформа перед origin «нормалізує» URL і прибирає з запитів невідомі query-параметри, зокрема `_rsc`. Що буде з RSC-запитами за замовчуванням?
> skill: routing · diff: 3 · id: nextjs-pl-routing-god-03
> - [ ] Нічого: `_rsc` — випадковий антикеш, сервер його ігнорує
> - [x] `307` на URL з правильним `_rsc`
> - [ ] Сервер віддасть payload
> - [ ] Сервер поверне `400 Bad Request` без пояснення причини
>
> **Пояснення:** `_rsc` — хеш заголовків, що впливають на відповідь: ключ кешу для CDN без підтримки `Vary`. RSC-запит без правильного `_rsc` сервер перенаправляє `307` на правильний (вимикається `experimental.validateRSCRequestHeaders`). Платформи, які рахують хеш самі, переписують запит заздалегідь, щоб уникнути зайвого round trip.

> [!quiz] Ви ввімкнули `partialPrefetching: true` і, «щоб було швидше», поставили `prefetch={true}` на всі 200 карток каталогу `/products/[id]`. Як це вплине на вартість prefetch?
> skill: routing · diff: 2 · id: nextjs-pl-routing-god-04
> - [ ] Ніяк: з Partial Prefetching усе одно береться один App Shell на маршрут
> - [ ] Prefetch вимкнеться
> - [ ] Кожна картка отримає повний рендер з «живими» даними складу
> - [x] Серверний виклик на кожну видиму картку
>
> **Пояснення:** за замовчуванням Partial Prefetching бере App Shell, спільний для всіх посилань маршруту, — вартість росте з кількістю маршрутів. `prefetch={true}` вмикає per-link prefetch: shell плюс закешований вміст за URL цього посилання (без «живих» даних, вони стрімляться після кліку). Це опція для кількох важливих посилань, не для сітки (тема 04 «Навігація під капотом»).

> [!quiz] Застосунок з `app/[lang]/layout.tsx` як root layout читає мову з cookie через `cookies()` у root layout, щоб поставити `<html lang>`. Яка архітектурна проблема і що радить 16.3?

> - [ ] Жодної: root layout рендериться один раз на сесію й кешується

> [!quiz] Поле пошуку має `key={useRouter().bfcacheId}`. Користувач вводить текст, переходить `Link` на іншу сторінку і тисне «Назад». Що в полі?

Як `key` він дає «з нуля на звичайному переході, як було на кнопці «Назад»». Документація радить його переважно для міграції старого коду (тема 04, розділ про `bfcacheId`).

> [!quiz] `/promo` вставляє `<style>{':root { --brand: red }'}</style>` і відео з автозапуском. Після `Link` на `/catalog` колір бренду лишився червоним, а звук грає далі. `cacheComponents: true`. Що відбувається?
> skill: routing · diff: 2 · id: nextjs-pl-routing-god-07
> - [ ] Next.js не встиг розмонтувати сторінку; це зникне через кілька секунд

Їх вимикають у cleanup `useLayoutEffect`, що виконується синхронно перед прихованням (тема 04, розділ про Activity).

## rendering

> [!quiz] Безпека вимагає CSP з nonce для всіх скриптів. Як це поєднується з Partial Prerendering?
> skill: rendering · diff: 1 · id: nextjs-pl-rendering-god-01
> - [ ] Ніяк не впливає: nonce додається до static shell під час збірки
> - [ ] Next.js генерує один nonce на деплой
> - [x] Несумісно: shell пререндерено без nonce
> - [ ] Працює, якщо nonce передати через `cookies()` у root layout
>
> **Пояснення:** nonce має бути унікальним на відповідь, а shell збирається один раз. Документація CSP прямо пише, що PPR несумісний з nonce-based CSP і що nonce вимагає динамічного рендеру. Тут справжній компроміс між жорсткою політикою і static shell.

> [!quiz] Чим `await io()` відрізняється від `await connection()` перед читанням `Date.now()` у Server Component?
> skill: rendering · diff: 2 · id: nextjs-pl-rendering-god-02
> - [ ] Нічим: `io` — новий псевдонім `connection` з іншого модуля
> - [x] `connection()` блокує prefetch, `io()` — ні
> - [ ] `io()` змушує весь маршрут рендеритися на кожен запит, `connection()` — лише компонент
> - [ ] `connection()` працює лише в Route Handlers, а в компонентах — `io()`
>
> **Пояснення:** `io()` (`next/cache`, 16.3) — маркер «далі I/O»: на запиті, у кеш-скоупі й у браузері він резолвиться одразу. `connection()` (`next/server`) тримає код до реальної навігації на сервер. Документація радить `io()`, якщо не потрібна саме семантика «лише на справжній запит».

> [!quiz] Сторінки стрімлять metadata, а SEO-команда скаржиться, що старий краулер партнера бачить порожній `<title>`. Яке налаштування для цього існує?
> skill: rendering · diff: 2 · id: nextjs-pl-rendering-god-03
> - [ ] `export const dynamic = 'force-static'` для всіх сторінок з metadata
> - [x] `htmlLimitedBots`: для вказаних User-Agent metadata стане блокуючою
> - [ ] Вимкнути `cacheComponents` для краулерів через Proxy за User-Agent
> - [ ] Перенести `generateMetadata` в Client Component під `<Suspense>`
>
> **Пояснення:** стрімінгова metadata може прийти вже в тілі стріму; браузери й сучасні боти її виконують, а «обмежені» краулери ні. Next.js має типовий список таких ботів, а `htmlLimitedBots` дозволяє задати свій регулярний вираз. Сегментні `dynamic` під Cache Components вже не працюють.

> [!quiz] Після переходу на стрімінг TTFB і FCP покращились, а LCP погіршився. Найімовірніша причина?
> skill: rendering · diff: 2 · id: nextjs-pl-rendering-god-04
> - [ ] Стрімінг завжди погіршує LCP через довше відкрите зʼєднання
> - [ ] Браузер не рахує LCP для стрімленого HTML
> - [x] LCP-елемент опинився в «дірці» `<Suspense>`
> - [ ] Shell став більшим через fallback-и, і браузер довше його розбирає
>
> **Пояснення:** LCP — момент появи найбільшого елемента, і якщо він за межею з повільним запитом, ранній shell не допомагає. LCP-елемент тримають у static shell (або в закешованому вмісті), а в дірки ставлять другорядне. Fallback-и без розмірів ще й псують CLS.

> [!quiz] Client Component рендерить `Date.now()`. Що радить документація для `cacheComponents: true`?
> skill: rendering · diff: 3 · id: nextjs-pl-rendering-god-05
> - [x] `use(io())` перед читанням `Date.now()`
> - [ ] Нічого: Client Components не пререндеряться, тож час завжди свіжий
> - [ ] Додати `'use cache'` у файл Client Component над компонентом
> - [ ] Обгорнути компонент у `connection()` з `next/server`
>
> **Пояснення:** SSR Client Components — частина пререндеру, тож синхронні джерела часу й випадковості вимагають того самого рішення, що й на сервері. `use(io())` суспендить компонент лише на пререндері, а в браузері й на запиті резолвиться одразу. `'use cache'` — директива серверних функцій і компонентів, не клієнтських. На 16.3.8 немаркований `Date.now()` у Client Component поза `<Suspense>` зупиняє пререндер, а всередині `<Suspense>` маршрут збирається статичним (○) з fallback у shell.

> [!quiz] Чим App Shell відрізняється від static shell?
> skill: rendering · diff: 3 · id: nextjs-pl-rendering-god-06
> - [x] App Shell — без URL-даних, для prefetch; static shell — перший HTML
> - [ ] Нічим: це дві назви одного пререндеру маршруту
> - [ ] App Shell — HTML першого заходу, static shell — payload для prefetch
> - [ ] App Shell існує лише на Vercel, static shell — на будь-якому хостингу

App Shell не залежить від `params` і `searchParams`, бере закешований вміст зі `stale` ≥ 5 хв, а для маршрутів з `cookies()`/`headers()` кешується на клієнті для сесії. Static shell — те, що миттєво йде у відповідь на документний запит, з дірками під `<Suspense>`.

> - [ ] Без PPR prefetch іде через `POST`, а `POST` CDN не кешує
>
> **Пояснення:** для PPR-маршруту static prefetch (заголовок `next-router-prefetch`) повертає той самий пререндер незалежно від стану роутера клієнта: `next-router-state-tree` не розбирається. CDN достатньо включити `_rsc` у ключ і поважати `Cache-Control`. Без PPR сервер читає стан роутера, щоб вирішити, які сегменти віддати, — варіантів відповіді більше. Prefetch — це `GET` з RSC-заголовками, а не `POST` (документація CDN caching).
