# Збереження чистоти компонентів

## Вступ

Деякі функції JavaScript є *чистими* — вони лише виконують обчислення і нічого більше. Записуючи компоненти як чисті функції, ви можете уникнути цілого класу помилок та непередбачуваної поведінки в міру зростання вашої кодової бази.

### Ви дізнаєтесь
* Що таке чистота і як вона допомагає уникати помилок
* Як зберігати компоненти чистими, не допускаючи змін під час фази рендерингу
* Як використовувати Strict Mode для пошуку помилок у ваших компонентах

---

## Чистота: Компоненти як формули

В інформатиці та функціональному програмуванні чиста функція має такі характеристики:

* **Займається своєю справою.** Вона не змінює жодних об'єктів чи змінних, які існували до її виклику.
* **Однакові входи, однаковий вихід.** За однакових вхідних даних чиста функція завжди повинна повертати однаковий результат.

### Приклад математичної формули

Розглянемо: `y = 2x`

- Якщо `x = 2`, тоді `y = 4`. Завжди.
- Якщо `x = 3`, тоді `y = 6`. Завжди.
- `y` не буде різним значенням залежно від часу доби чи інших зовнішніх факторів.

### Приклад на JavaScript

```js
function double(number) {
  return 2 * number;
}
```

`double` — це чиста функція. Якщо ви передасте їй `3`, вона поверне `6`. Завжди.

### Компоненти React як чисті функції

**React припускає, що кожен компонент, який ви пишете, є чистою функцією.** Це означає, що компоненти React повинні завжди повертати однаковий JSX за однакових вхідних даних.

#### Приклад: Компонент рецепта

```js
function Recipe({ drinkers }) {
  return (
    <ol>
      <li>Boil {drinkers} cups of water.</li>
      <li>Add {drinkers} spoons of tea and {0.5 * drinkers} spoons of spice.</li>
      <li>Add {0.5 * drinkers} cups of milk to boil and sugar to taste.</li>
    </ol>
  );
}

export default function App() {
  return (
    <section>
      <h1>Spiced Chai Recipe</h1>
      <h2>For two</h2>
      <Recipe drinkers={2} />
      <h2>For a gathering</h2>
      <Recipe drinkers={4} />
    </section>
  );
}
```

Коли ви передаєте `drinkers={2}` компоненту `Recipe`, він поверне JSX з `2 cups of water`. Завжди. Якщо передати `drinkers={4}`, він поверне JSX з `4 cups of water`. Завжди.

Думайте про компоненти як про рецепти: якщо ви дотримуєтесь їх і не додаєте нових інгредієнтів під час приготування, ви отримаєте ту саму страву кожного разу.

## Побічні ефекти: (не)навмисні наслідки

Процес рендерингу React повинен завжди бути чистим. Компоненти повинні лише *повертати* свій JSX, а не *змінювати* будь-які об'єкти чи змінні, які існували до рендерингу — це зробило б їх нечистими.

### Зламаний приклад: Нечистий компонент

```js
let guest = 0;

function Cup() {
  // Погано: зміна попередньо існуючої змінної!
  guest = guest + 1;
  return <h2>Tea cup for guest #{guest}</h2>;
}

export default function TeaSet() {
  return (
    <>
      <Cup />
      <Cup />
      <Cup />
    </>
  );
}
```

Цей компонент читає та записує змінну `guest`, оголошену за його межами. Виклик цього компонента кілька разів створює різний JSX, і інші компоненти, що читають `guest`, створюватимуть різний JSX залежно від того, коли вони були відрендерені. Це непередбачувано і призводить до заплутаних помилок.

### Виправлений приклад: Використання props

```js
function Cup({ guest }) {
  return <h2>Tea cup for guest #{guest}</h2>;
}

export default function TeaSet() {
  return (
    <>
      <Cup guest={1} />
      <Cup guest={2} />
      <Cup guest={3} />
    </>
  );
}
```

Тепер компонент чистий — JSX, який він повертає, залежить лише від prop `guest`.

### Ключовий принцип

Компоненти не повинні залежати від послідовності рендерингу один одного. Кожен компонент повинен "думати самостійно" і не намагатися координуватися з іншими або залежати від них під час рендерингу. Рендеринг — як шкільний іспит: кожен компонент повинен обчислювати JSX самостійно.

## Глибоке занурення: Виявлення нечистих обчислень за допомогою StrictMode

Під час рендерингу ви можете читати три види вхідних даних:
* Props
* State
* Context

Ви повинні завжди ставитися до них як до даних лише для читання.

Коли ви хочете *змінити* щось у відповідь на введення користувача, вам слід встановити state замість запису в змінну. Ніколи не змінюйте попередньо існуючі змінні або об'єкти під час рендерингу вашого компонента.

### React Strict Mode

**React пропонує "Strict Mode", в якому він викликає функцію кожного компонента двічі під час розробки.** Викликаючи функції компонентів двічі, Strict Mode допомагає знаходити компоненти, які порушують правила чистоти.

В оригінальному зламаному прикладі вихід відображав "Guest #2", "Guest #4" та "Guest #6" замість "Guest #1", "Guest #2" та "Guest #3", тому що функція була нечистою і подвійний виклик зламав її. Виправлена чиста версія працює навіть при подвійному виклику функції — чисті функції лише обчислюють, тому їх подвійний виклик нічого не змінює.

Strict Mode не впливає на продакшн. Щоб увімкнути Strict Mode, оберніть кореневий компонент у `<React.StrictMode>`. Деякі фреймворки роблять це за замовчуванням.

## Локальна мутація: Маленький секрет вашого компонента

Проблема в попередніх прикладах полягала у зміні *попередньо існуючої* змінної під час рендерингу (що називається **"мутацією"**). Чисті функції не мутують змінні за межами області видимості функції або об'єкти, створені до виклику.

**Однак, цілком нормально змінювати змінні та об'єкти, які ви *щойно* створили під час рендерингу.**

### Приклад: Локальна мутація

```js
function Cup({ guest }) {
  return <h2>Tea cup for guest #{guest}</h2>;
}

export default function TeaGathering() {
  const cups = [];
  for (let i = 1; i <= 12; i++) {
    cups.push(<Cup key={i} guest={i} />);
  }
  return cups;
}
```

Якби `cups` або масив `[]` були створені за межами `TeaGathering`, це було б проблемою. Однак це нормально, оскільки ви створили їх *під час того самого рендеру*, всередині `TeaGathering`. Жоден код за межами `TeaGathering` ніколи не дізнається, що це сталося. Це називається **"локальна мутація"** — маленький секрет вашого компонента.

## Де *можна* створювати побічні ефекти

Хоча функціональне програмування покладається на чистоту, в якийсь момент *щось* має змінитися. Ці зміни — оновлення екрану, запуск анімації, зміна даних — називаються **побічними ефектами.** Вони відбуваються _"збоку"_, не під час рендерингу.

### Обробники подій

**Побічні ефекти зазвичай належать обробникам подій.** Обробники подій — це функції, які React запускає, коли ви виконуєте дію (наприклад, натискаєте кнопку). Хоча обробники подій визначаються *всередині* вашого компонента, вони не виконуються *під час* рендерингу. **Тому обробники подій не повинні бути чистими.**

### useEffect

Якщо ви не можете знайти відповідний обробник подій для вашого побічного ефекту, ви можете прикріпити його до поверненого JSX за допомогою виклику `useEffect` у вашому компоненті. Це повідомляє React виконати його пізніше, після рендерингу, коли побічні ефекти дозволені. **Цей підхід повинен бути вашим останнім засобом.**

Коли можливо, намагайтеся виразити вашу логіку лише за допомогою рендерингу.

## Глибоке занурення: Чому React турбується про чистоту?

Написання чистих функцій вимагає звички та дисципліни, але це відкриває чудові можливості:

* **Серверний рендеринг:** Компоненти можуть виконуватися в різних середовищах (наприклад, на сервері). Оскільки вони повертають однаковий результат за однакових вхідних даних, один компонент може обслуговувати багато запитів користувачів.
* **Оптимізація продуктивності:** Ви можете покращити продуктивність, пропускаючи рендеринг компонентів, вхідні дані яких не змінилися. Це безпечно, оскільки чисті функції завжди повертають однакові результати, тому їх безпечно кешувати.
* **Відновлення після помилок:** Якщо дані змінюються в середині рендерингу глибокого дерева компонентів, React може перезапустити рендеринг, не витрачаючи час на завершення застарілого рендеру. Чистота робить безпечним зупинку обчислень у будь-який момент.

Кожна нова функція React використовує переваги чистоти. Від завантаження даних до анімацій та продуктивності — збереження чистоти компонентів розкриває потужність парадигми React.

---

## Підсумок

* Компонент повинен бути чистим, тобто:
  * **Займається своєю справою.** Він не повинен змінювати жодних об'єктів чи змінних, які існували до рендерингу.
  * **Однакові входи, однаковий вихід.** За однакових вхідних даних компонент повинен завжди повертати однаковий JSX.
* Рендеринг може відбутися в будь-який час, тому компоненти не повинні залежати від послідовності рендерингу один одного.
* Ви не повинні мутувати жодних вхідних даних, які ваші компоненти використовують для рендерингу (props, state, context). Щоб оновити екран, "встановлюйте" state замість мутування попередньо існуючих об'єктів.
* Прагніть виразити логіку компонента в JSX, який ви повертаєте. Коли потрібно "змінити речі", робіть це в обробнику подій. Як останній засіб — використовуйте `useEffect`.
* Написання чистих функцій вимагає практики, але це розкриває потужність парадигми React.

## Завдання

### Завдання 1: Виправте зламаний годинник

**Проблема:** Компонент намагається встановити CSS-клас `<h1>` на `"night"` з опівночі до 6 ранку та `"day"` в інший час, але це не працює.

**Зламаний код:**
```js
export default function Clock({ time }) {
  const hours = time.getHours();
  if (hours >= 0 && hours <= 6) {
    document.getElementById('time').className = 'night';
  } else {
    document.getElementById('time').className = 'day';
  }
  return (
    <h1 id="time">
      {time.toLocaleTimeString()}
    </h1>
  );
}
```

**Рішення:** Обчисліть `className` та включіть його у вихід рендерингу:

```js
export default function Clock({ time }) {
  const hours = time.getHours();
  let className;
  if (hours >= 0 && hours <= 6) {
    className = 'night';
  } else {
    className = 'day';
  }
  return (
    <h1 className={className}>
      {time.toLocaleTimeString()}
    </h1>
  );
}
```

Побічний ефект (модифікація DOM) був непотрібним. Потрібно було лише повернути JSX.

### Завдання 2: Виправте зламаний профіль

**Проблема:** Два компоненти `Profile`, відрендерені поруч, показують різні дані. При згортанні та розгортанні першого профілю обидва показують ту саму особу — баг.

**Зламаний код:**
```js
let currentPerson;

export default function Profile({ person }) {
  currentPerson = person;
  return (
    <Panel>
      <Header />
      <Avatar />
    </Panel>
  )
}

function Header() {
  return <h1>{currentPerson.name}</h1>;
}

function Avatar() {
  return (
    <img
      className="avatar"
      src={getImageUrl(currentPerson)}
      alt={currentPerson.name}
      width={50}
      height={50}
    />
  );
}
```

**Рішення:** Видаліть змінну `currentPerson` та передавайте інформацію через props:

```js
export default function Profile({ person }) {
  return (
    <Panel>
      <Header person={person} />
      <Avatar person={person} />
    </Panel>
  )
}

function Header({ person }) {
  return <h1>{person.name}</h1>;
}

function Avatar({ person }) {
  return (
    <img
      className="avatar"
      src={getImageUrl(person)}
      alt={person.name}
      width={50}
      height={50}
    />
  );
}
```

Все спілкування повинно відбуватися через props. Не встановлюйте змінні для комунікації між компонентами.

### Завдання 3: Виправте зламану стрічку історій

**Проблема:** Компонент `StoryTray` додає заповнювач "Create Story" у отриманий масив stories, але "Create Story" з'являється більше одного разу.

**Зламаний код:**
```js
export default function StoryTray({ stories }) {
  stories.push({
    id: 'create',
    label: 'Create Story'
  });

  return (
    <ul>
      {stories.map(story => (
        <li key={story.id}>
          {story.label}
        </li>
      ))}
    </ul>
  );
}
```

**Рішення 1:** Рендеріть "Create Story" окремо без мутування масиву:

```js
export default function StoryTray({ stories }) {
  return (
    <ul>
      {stories.map(story => (
        <li key={story.id}>
          {story.label}
        </li>
      ))}
      <li>Create Story</li>
    </ul>
  );
}
```

**Рішення 2:** Скопіюйте масив перед мутуванням:

```js
export default function StoryTray({ stories }) {
  // Скопіюйте масив!
  const storiesToDisplay = stories.slice();

  // Не впливає на оригінальний масив:
  storiesToDisplay.push({
    id: 'create',
    label: 'Create Story'
  });

  return (
    <ul>
      {storiesToDisplay.map(story => (
        <li key={story.id}>
          {story.label}
        </li>
      ))}
    </ul>
  );
}
```

Пам'ятайте: `push`, `pop`, `reverse` та `sort` мутують оригінальний масив. `slice`, `filter` та `map` створюють новий.
