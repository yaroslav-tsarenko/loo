# Створення застосунку React з нуля

## Вступ

Якщо ваш застосунок має обмеження, які погано обслуговуються існуючими фреймворками, ви віддаєте перевагу створенню власного фреймворку або просто хочете вивчити основи застосунку React, ви можете створити застосунок React з нуля.

---

## Розгляньте використання фреймворку

Початок з нуля — це простий спосіб почати використовувати React, але основний компроміс полягає в тому, що цей шлях часто рівнозначний створенню власного ad-hoc фреймворку. У міру розвитку ваших вимог вам може знадобитися вирішувати більше проблем рівня фреймворку, для яких наші рекомендовані фреймворки вже мають добре розроблені та підтримувані рішення.

Наприклад, якщо в майбутньому вашому застосунку знадобиться підтримка серверного рендерингу (SSR), генерації статичних сайтів (SSG) та/або React Server Components (RSC), вам доведеться реалізовувати це самостійно. Аналогічно, майбутні функції React, які вимагають інтеграції на рівні фреймворку, доведеться впроваджувати самостійно, якщо ви захочете їх використовувати.

Наші рекомендовані фреймворки також допомагають створювати більш продуктивні застосунки. Наприклад, зменшення або усунення каскадних мережевих запитів забезпечує кращий досвід користувача. Це може не бути пріоритетом при створенні навчального проєкту, але якщо ваш застосунок отримає користувачів, ви, можливо, захочете покращити його продуктивність.

Цей шлях також ускладнює отримання підтримки, оскільки ваш спосіб розробки маршрутизації, завантаження даних та інших функцій буде унікальним для вашої ситуації. Обирайте цей варіант лише якщо ви готові вирішувати ці проблеми самостійно або впевнені, що ці функції вам ніколи не знадобляться.

Для списку рекомендованих фреймворків дивіться [Створення застосунку React](/learn/creating-a-react-app).

---

## Крок 1: Встановіть інструмент збірки

Першим кроком є встановлення інструменту збірки, такого як `vite`, `parcel` або `rsbuild`. Ці інструменти надають функції для пакування та запуску вихідного коду, сервер розробки для локальної розробки та команду збірки для розгортання застосунку на продакшен-сервері.

### Vite

[Vite](https://vite.dev/) — це інструмент збірки, який прагне забезпечити швидший та легший досвід розробки для сучасних веб-проєктів.

```bash
npm create vite@latest my-app -- --template react-ts
```

Vite має власну думку щодо конфігурації та постачається з розумними налаштуваннями за замовчуванням. Vite має багату екосистему плагінів для підтримки швидкого оновлення, JSX, Babel/SWC та інших поширених функцій. Дивіться [плагін React для Vite](https://vite.dev/plugins/#vitejs-plugin-react) або [плагін React SWC](https://vite.dev/plugins/#vitejs-plugin-react-swc) та [приклад проєкту React SSR](https://vite.dev/guide/ssr.html#example-projects) для початку.

Vite вже використовується як інструмент збірки в одному з наших [рекомендованих фреймворків](/learn/creating-a-react-app): [React Router](https://reactrouter.com/start/framework/installation).

### Parcel

[Parcel](https://parceljs.org/) поєднує чудовий досвід розробки з нуля та масштабовану архітектуру, яка може провести ваш проєкт від початку до масивних продакшен-застосунків.

```bash
npm install --save-dev parcel
```

Parcel підтримує швидке оновлення, JSX, TypeScript, Flow та стилізацію з коробки. Дивіться [рецепт Parcel для React](https://parceljs.org/recipes/react/#getting-started) для початку.

### Rsbuild

[Rsbuild](https://rsbuild.dev/) — це інструмент збірки на базі Rspack, який забезпечує безперебійний досвід розробки для застосунків React. Він постачається з ретельно налаштованими значеннями за замовчуванням та оптимізаціями продуктивності, готовими до використання.

```bash
npx create-rsbuild --template react
```

Rsbuild включає вбудовану підтримку функцій React, таких як швидке оновлення, JSX, TypeScript та стилізація. Дивіться [гайд Rsbuild для React](https://rsbuild.dev/guide/framework/react) для початку.

### Metro для React Native

Якщо ви починаєте з нуля з React Native, вам потрібно використовувати [Metro](https://metrobundler.dev/) — JavaScript-бандлер для React Native. Metro підтримує бандлінг для платформ як iOS та Android, але має менше функцій порівняно з інструментами тут. Ми рекомендуємо починати з Vite, Parcel або Rsbuild, якщо ваш проєкт не вимагає підтримки React Native.

## Крок 2: Побудуйте поширені патерни застосунку

Інструменти збірки, перелічені вище, починають з клієнтського односторінкового застосунку (SPA), але не включають подальших рішень для поширеної функціональності, такої як маршрутизація, завантаження даних або стилізація.

Екосистема React включає багато інструментів для цих проблем. Ми перелічили кілька широко використовуваних як відправну точку, але ви можете обрати інші інструменти, якщо вони краще підходять вам.

### Маршрутизація

Маршрутизація визначає, який контент або сторінки відображати, коли користувач відвідує певний URL. Вам потрібно налаштувати маршрутизатор для відповідності URL різним частинам вашого застосунку. Вам також потрібно обробляти вкладені маршрути, параметри маршрутів та параметри запитів. Маршрутизатори можуть бути налаштовані у вашому коді або визначені на основі структури папок та файлів компонентів.

Маршрутизатори — це ключова частина сучасних застосунків і зазвичай інтегруються із завантаженням даних (включаючи попереднє завантаження даних для всієї сторінки для швидшого завантаження), розділенням коду (для мінімізації розміру клієнтських бандлів) та підходами до рендерингу сторінок (для визначення як генерується кожна сторінка).

Ми пропонуємо використовувати:

- [React Router](https://reactrouter.com/start/data/custom)
- [Tanstack Router](https://tanstack.com/router/latest)

### Завантаження даних

Отримання даних з сервера або іншого джерела даних — ключова частина більшості застосунків. Правильне виконання цього вимагає обробки станів завантаження, помилок та кешування отриманих даних, що може бути складним.

Спеціалізовані бібліотеки для завантаження даних виконують складну роботу з отримання та кешування даних за вас, дозволяючи зосередитися на тому, які дані потрібні вашому застосунку та як їх відображати. Ці бібліотеки зазвичай використовуються безпосередньо у ваших компонентах, але також можуть бути інтегровані у завантажувачі маршрутів для швидшого попереднього завантаження та кращої продуктивності, а також у серверному рендерингу.

Зверніть увагу, що завантаження даних безпосередньо в компонентах може призвести до повільнішого завантаження через каскади мережевих запитів, тому ми рекомендуємо попереднє завантаження даних у завантажувачах маршрутів або на сервері, де це можливо! Це дозволяє отримати всі дані сторінки одночасно під час її відображення.

Якщо ви отримуєте дані з більшості бекендів або REST-стиль API, ми пропонуємо використовувати:

- [TanStack Query](https://tanstack.com/query/)
- [SWR](https://swr.vercel.app/)
- [RTK Query](https://redux-toolkit.js.org/rtk-query/overview)

Якщо ви отримуєте дані з GraphQL API, ми пропонуємо використовувати:

- [Apollo](https://www.apollographql.com/docs/react)
- [Relay](https://relay.dev/)

### Розділення коду

Розділення коду — це процес розбиття вашого застосунку на менші бандли, які можуть бути завантажені за потребою. Розмір коду застосунку збільшується з кожною новою функцією та додатковою залежністю. Застосунки можуть повільно завантажуватися, оскільки весь код для всього застосунку потрібно надіслати перед використанням. Кешування, зменшення функцій/залежностей та перенесення коду для виконання на сервері можуть допомогти пом'якшити повільне завантаження, але є неповними рішеннями, які можуть жертвувати функціональністю при надмірному використанні.

Аналогічно, якщо ви покладаєтесь на застосунки з вашим фреймворком для розділення коду, можуть виникнути ситуації, коли завантаження стає повільнішим, ніж якби розділення коду не виконувалося взагалі. Наприклад, [лінива завантаження](/reference/react/lazy) графіка затримує відправку коду, необхідного для рендерингу графіка, відокремлюючи код графіка від решти застосунку. [Parcel підтримує розділення коду з React.lazy](https://parceljs.org/recipes/react/#code-splitting). Однак якщо графік завантажує свої дані *після* початкового рендерингу, ви тепер чекаєте двічі. Це каскад: замість одночасного отримання даних для графіка та надсилання коду для його рендерингу, ви повинні чекати завершення кожного кроку по черзі.

Розділення коду за маршрутом, інтегроване з бандлінгом та завантаженням даних, може зменшити початковий час завантаження застосунку та час рендерингу найбільшого видимого контенту ([Largest Contentful Paint](https://web.dev/articles/lcp)).

Для інструкцій з розділення коду дивіться документацію вашого інструменту збірки:

- [Оптимізації збірки Vite](https://vite.dev/guide/features.html#build-optimizations)
- [Розділення коду Parcel](https://parceljs.org/features/code-splitting/)
- [Розділення коду Rsbuild](https://rsbuild.dev/guide/optimization/code-splitting)

### Покращення продуктивності застосунку

Оскільки обраний вами інструмент збірки підтримує лише односторінкові застосунки (SPA), вам потрібно реалізувати інші [патерни рендерингу](https://www.patterns.dev/vanilla/rendering-patterns), такі як серверний рендеринг (SSR), генерація статичних сайтів (SSG) та/або React Server Components (RSC). Навіть якщо ці функції не потрібні спочатку, в майбутньому деякі маршрути можуть отримати переваги від SSR, SSG або RSC.

* **Односторінкові застосунки (SPA)** завантажують одну HTML-сторінку та динамічно оновлюють її при взаємодії користувача. SPA простіше розпочати, але можуть мати повільніший початковий час завантаження. SPA — це архітектура за замовчуванням для більшості інструментів збірки.

* **Потоковий серверний рендеринг (SSR)** рендерить сторінку на сервері та надсилає повністю відрендеровану сторінку клієнту. SSR може покращити продуктивність, але може бути складнішим у налаштуванні та підтримці, ніж SPA. З додаванням потокової передачі SSR може бути дуже складним у налаштуванні та підтримці. Дивіться [гайд SSR Vite](https://vite.dev/guide/ssr).

* **Генерація статичних сайтів (SSG)** генерує статичні HTML-файли для вашого застосунку під час збірки. SSG може покращити продуктивність, але може бути складнішим у налаштуванні та підтримці, ніж серверний рендеринг. Дивіться [гайд SSG Vite](https://vite.dev/guide/ssr.html#pre-rendering-ssg).

* **React Server Components (RSC)** дозволяють змішувати компоненти часу збірки, серверні та інтерактивні компоненти в одному дереві React. RSC може покращити продуктивність, але наразі вимагає глибокої експертизи для налаштування та підтримки. Дивіться [приклади RSC Parcel](https://github.com/parcel-bundler/rsc-examples).

Ваші стратегії рендерингу повинні інтегруватися з маршрутизатором, щоб застосунки, побудовані з вашим фреймворком, могли обирати стратегію рендерингу на рівні кожного маршруту. Це дозволить використовувати різні стратегії рендерингу без переписування всього застосунку. Наприклад, лендінг-сторінка вашого застосунку може отримати переваги від статичної генерації (SSG), тоді як сторінка зі стрічкою контенту може найкраще працювати з серверним рендерингом.

Використання правильної стратегії рендерингу для правильних маршрутів може зменшити час завантаження першого байту контенту ([Time to First Byte](https://web.dev/articles/ttfb)), першого фрагменту контенту для рендерингу ([First Contentful Paint](https://web.dev/articles/fcp)) та найбільшого видимого контенту застосунку для рендерингу ([Largest Contentful Paint](https://web.dev/articles/lcp)).

### І ще...

Це лише кілька прикладів функцій, які новому застосунку потрібно враховувати при створенні з нуля. Багато обмежень, з якими ви зіткнетесь, важко вирішити, оскільки кожна проблема взаємопов'язана з іншими та може вимагати глибокої експертизи в проблемних областях, з якими ви, можливо, не знайомі.

Якщо ви не хочете вирішувати ці проблеми самостійно, ви можете [почати з фреймворку](/learn/creating-a-react-app), який надає ці функції з коробки.
