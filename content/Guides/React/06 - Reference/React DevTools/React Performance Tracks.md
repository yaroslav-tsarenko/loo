# React Performance Tracks

## Вступ

React Performance tracks — це спеціалізовані користувацькі записи, які з'являються на панелі Performance вашого браузера. Вони надають розробникам комплексне уявлення про продуктивність їхнього React додатку, візуалізуючи специфічні для React події та метрики поряд з іншими критичними джерелами даних, такими як мережеві запити, виконання JavaScript та активність event loop — усе синхронізовано на єдиній шкалі часу панелі Performance для повного розуміння поведінки додатку.

## Використання

React Performance tracks доступні лише в development та profiling збірках React:

- **Development**: увімкнено за замовчуванням.
- **Profiling**: За замовчуванням увімкнено лише Scheduler tracks. Components track показує лише компоненти, що знаходяться в піддеревах, обгорнутих `<Profiler>`. Якщо у вас увімкнено розширення React Developer Tools, усі компоненти включаються в Components track, навіть якщо вони не обгорнуті `<Profiler>`. Server tracks недоступні в profiling збірках.

Якщо увімкнено, tracks повинні автоматично з'являтися в трейсах, які ви записуєте на панелі Performance браузерів, що надають API розширюваності.

> **Примітка**: Інструментація профілювання, яка забезпечує React Performance tracks, додає деяке додаткове навантаження, тому вона вимкнена в production збірках за замовчуванням. Server Components та Server Requests tracks доступні лише в development збірках.

### Використання Profiling збірок

На додаток до production та development збірок, React включає спеціальну profiling збірку. Для використання profiling збірок:

1. Використовуйте `react-dom/profiling` замість `react-dom/client`
2. Створіть alias `react-dom/client` на `react-dom/profiling` під час збірки через налаштування бандлера замість ручного оновлення кожного імпорту `react-dom/client`
3. Ваш фреймворк може мати вбудовану підтримку для увімкнення profiling збірки React

## Tracks

### Scheduler

Scheduler — це внутрішня концепція React, що використовується для управління задачами з різними пріоритетами. Цей track складається з 4 підтреків, кожен з яких представляє роботу конкретного пріоритету:

- **Blocking** — Синхронні оновлення, які могли бути ініційовані взаємодіями користувача.
- **Transition** — Неблокуюча робота, що відбувається у фоновому режимі, зазвичай ініційована через `startTransition`.
- **Suspense** — Робота, пов'язана з Suspense boundaries, така як відображення fallback або відкриття контенту.
- **Idle** — Робота з найнижчим пріоритетом, яка виконується, коли немає інших задач з вищим пріоритетом.

#### Рендери

Кожен прохід рендерингу складається з кількох фаз, видимих на шкалі часу:

- **Update** — Що спричинило новий прохід рендерингу.
- **Render** — React рендерить оновлене піддерево, викликаючи render функції компонентів. Ви можете бачити піддерево відрендерених компонентів на Components track, який дотримується тієї ж колірної схеми.
- **Commit** — Після рендерингу компонентів React застосовує зміни до DOM та запускає layout effects, як-от `useLayoutEffect`.
- **Remaining Effects** — React запускає passive effects відрендереного піддерева. Зазвичай це відбувається після paint, і саме тоді React запускає хуки, як-от `useEffect`. Один відомий виняток — взаємодії користувача, як-от кліки, або інші дискретні події. У цьому сценарії ця фаза може запуститися перед paint.

#### Каскадні оновлення

Каскадні оновлення — це патерн для регресій продуктивності. Якщо оновлення було заплановано під час проходу рендерингу, React може відкинути завершену роботу та почати новий прохід.

У development збірках React показує, який компонент запланував нове оновлення. Це включає як звичайні оновлення, так і каскадні. Ви можете побачити розширений stack trace, натиснувши на запис "Cascading update", який показує ім'я методу, що запланував оновлення.

### Components

Components track візуалізує тривалість React компонентів у вигляді flamegraph, де кожен запис представляє тривалість рендерингу відповідного компонента та всіх його дочірніх компонентів.

Аналогічно, тривалості effects представлені як flamegraph, але з іншою колірною схемою, що відповідає відповідній фазі на Scheduler track.

> **Примітка**: На відміну від рендерів, не всі effects показуються на Components track за замовчуванням. Для підтримки продуктивності та запобігання захаращення UI, React показує лише effects, тривалість яких становила 0.05мс або більше, або ті, що ініціювали оновлення.

#### Додаткові події

Додаткові події можуть відображатися під час фаз render та effects:

- **Mount** — Відповідне піддерево рендерів компонентів або effects було змонтовано.
- **Unmount** — Відповідне піддерево рендерів компонентів або effects було демонтовано.
- **Reconnect** — Подібно до Mount, але обмежено випадками використання `<Activity>`.
- **Disconnect** — Подібно до Unmount, але обмежено випадками використання `<Activity>`.

#### Змінені Props

У development збірках, коли ви натискаєте на запис рендерингу компонента, ви можете перевірити потенційні зміни в props. Ви можете використовувати цю інформацію для ідентифікації непотрібних рендерів.

### Server

#### Server Requests

Server Requests track візуалізує всі Promises, які в кінцевому підсумку потрапляють у React Server Component. Це включає будь-які `async` операції, як-от виклики `fetch` або асинхронні файлові операції Node.js.

React намагається об'єднати Promises, що запускаються зсередини стороннього коду, в один span, що представляє тривалість усієї операції, яка блокує код першої сторони. Наприклад, метод сторонньої бібліотеки `getUser`, який внутрішньо викликає `fetch` кілька разів, буде представлений як один span під назвою `getUser`, замість показу кількох span `fetch`.

Натискання на spans показує:
- Stack trace місця створення Promise
- Перегляд значення, з яким Promise було resolved (якщо доступно)

Rejected Promises відображаються червоним кольором із їхнім значенням відхилення.

#### Server Components

Server Components track візуалізує тривалість React Server Components та Promises, які вони очікували. Тайміги відображаються як flamegraph, де кожен запис представляє тривалість рендерингу відповідного компонента та всіх його дочірніх компонентів.

Якщо ви await Promise, React відображає тривалість цього Promise. Для перегляду всіх I/O операцій використовуйте Server Requests track.

Різні кольори вказують на тривалість рендерингу компонента. Чим темніший колір, тим довша тривалість.

Server Components track group завжди містить "Primary" track. Якщо React може рендерити Server Components паралельно, він відображає додаткові "Parallel" tracks. Якщо більше 8 Server Components рендеряться одночасно, React асоціює їх з останнім "Parallel" track замість додавання нових tracks.
