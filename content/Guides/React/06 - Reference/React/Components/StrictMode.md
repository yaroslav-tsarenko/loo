# `<StrictMode>`

## Огляд

`<StrictMode>` — це компонент React, який вмикає додаткові поведінки та попередження лише для розробки, щоб допомогти ідентифікувати поширені помилки у ваших компонентах під час розробки.

```js
<StrictMode>
  <App />
</StrictMode>
```

---

## Довідка

### `<StrictMode>`

Використовуйте `StrictMode`, щоб увімкнути додаткові поведінки розробки та попередження для дерева компонентів всередині:

```js
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'));
root.render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

#### Увімкнені поведінки

Строгий режим вмикає наступні поведінки лише для розробки:

- **Подвійний рендеринг**: Ваші компоненти будуть рендеритися додатковий раз для пошуку помилок, спричинених нечистим рендерингом
- **Повторний запуск ефектів**: Ваші компоненти будуть повторно запускати Effects додатковий раз для пошуку помилок, спричинених відсутністю очищення Effect
- **Повторний запуск колбеків ref**: Ваші компоненти будуть повторно запускати колбеки ref додатковий раз для пошуку помилок, спричинених відсутністю очищення ref
- **Перевірки застарілих API**: Ваші компоненти будуть перевірятися на використання застарілих API

#### Пропси

`StrictMode` не приймає жодних пропсів.

#### Застереження

- Немає способу вимкнути Strict Mode всередині дерева, обгорнутого у `<StrictMode>`. Це дає впевненість, що всі компоненти всередині перевіряються. Якщо команди не погоджуються щодо цінності перевірок, їм потрібно дійти консенсусу або перемістити `<StrictMode>` нижче в дереві.

---

## Використання

### Увімкнення Strict Mode для всього застосунку

Щоб увімкнути Strict Mode для всього застосунку, обгорніть кореневий компонент у `<StrictMode>` при рендерингу:

```js
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'));
root.render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

**Рекомендація**: Обгортайте весь застосунок у Strict Mode, особливо для новостворених застосунків. Якщо ви використовуєте фреймворк, який викликає `createRoot` за вас, перевірте його документацію щодо увімкнення Strict Mode.

**Важливо**: Хоча перевірки Strict Mode виконуються лише в режимі розробки, вони допомагають знаходити помилки, які вже існують у вашому коді, але їх важко надійно відтворити у продакшні. Strict Mode дозволяє виправляти помилки до того, як їх повідомлять користувачі.

> **Примітка**: Усі перевірки Strict Mode виконуються лише в режимі розробки і не впливають на продакшн-збірку.

---

### Увімкнення Strict Mode для частини застосунку

Ви також можете увімкнути Strict Mode для будь-якої частини вашого застосунку:

```js
import { StrictMode } from 'react';

function App() {
  return (
    <>
      <Header />
      <StrictMode>
        <main>
          <Sidebar />
          <Content />
        </main>
      </StrictMode>
      <Footer />
    </>
  );
}
```

У цьому прикладі перевірки Strict Mode не будуть виконуватися для компонентів `Header` та `Footer`. Однак вони будуть виконуватися для `Sidebar` та `Content`, а також усіх компонентів всередині них, незалежно від глибини вкладеності.

> **Примітка**: Коли `StrictMode` увімкнено для частини застосунку, React вмикатиме лише ті поведінки, які можливі у продакшні. Наприклад, якщо `<StrictMode>` не увімкнено в корені застосунку, він не буде повторно запускати Effects при початковому монтуванні, оскільки це призвело б до подвійного спрацювання дочірніх ефектів без батьківських, що не може статися у продакшні.

## Виправлення помилок, знайдених подвійним рендерингом у розробці

React припускає, що кожен компонент, який ви пишете, є чистою функцією — компоненти завжди повинні повертати той самий JSX за однакових вхідних даних (пропси, стан та контекст).

Компоненти, які порушують це правило, поводяться непередбачувано та спричиняють помилки. Щоб допомогти знайти випадково нечистий код, Strict Mode викликає деякі функції (тільки ті, що мають бути чистими) **двічі у режимі розробки**. Це включає:

- Тіло функції вашого компонента (лише логіка верхнього рівня, без коду всередині обробників подій)
- Функції, які ви передаєте у `useState`, функції `set`, `useMemo` або `useReducer`
- Деякі методи класових компонентів, такі як `constructor`, `render`, `shouldComponentUpdate`

Якщо функція чиста, подвійний запуск не змінює її поведінку, оскільки чиста функція дає той самий результат кожного разу. Однак якщо функція нечиста (наприклад, мутує дані, які отримує), подвійний запуск зазвичай помітний (саме це робить її нечистою!). Це допомагає виявити та виправити помилку на ранньому етапі.

### Приклад: Помилка, знайдена подвійним рендерингом

Компонент `StoryTray` приймає масив `stories` та додає один останній елемент "Create Story" в кінці:

#### Початковий помилковий код:

```js
export default function StoryTray({ stories }) {
  const items = stories;
  items.push({ id: 'create', label: 'Create Story' });
  return (
    <ul>
      {items.map(story => (
        <li key={story.id}>
          {story.label}
        </li>
      ))}
    </ul>
  );
}
```

**Проблема**: Цей компонент безпосередньо змінює масив `stories` з пропсів. Кожного разу при рендерингу він знову додає "Create Story". Компонент не є чистим — багаторазовий запуск дає різні результати.

#### Без Strict Mode

Помилка спочатку не очевидна, але стає помітною, коли компонент перерендерюється кілька разів (наприклад, при наведенні курсора).

#### З Strict Mode

Strict Mode викликає вашу функцію рендерингу двічі, тому ви одразу бачите помилку — "Create Story" з'являється двічі при початковому рендерингу.

#### Виправлений код:

```js
export default function StoryTray({ stories }) {
  const items = stories.slice(); // Клонуємо масив
  // Добре: додаємо у новий масив
  items.push({ id: 'create', label: 'Create Story' });
  return (
    <ul>
      {items.map(story => (
        <li key={story.id}>
          {story.label}
        </li>
      ))}
    </ul>
  );
}
```

Це робить функцію `StoryTray` чистою. Кожного разу при виклику вона змінює лише нову копію масиву і не впливає на зовнішні об'єкти чи змінні.

**Перевага**: Коли ви виправляєте компонент для правильного рендерингу у Strict Mode, ви також виправляєте багато можливих майбутніх продакшн-помилок.

## Виправлення помилок, знайдених повторним запуском ефектів у розробці

Strict Mode допомагає знаходити помилки в Effects.

Кожен Effect має код налаштування та може мати код очищення. Зазвичай:
- React викликає налаштування при монтуванні компонента
- React викликає очищення при демонтуванні компонента
- React викликає очищення та налаштування знову, якщо залежності змінилися

Коли Strict Mode увімкнено, React також виконує **один додатковий цикл налаштування+очищення у розробці для кожного Effect**. Це допомагає виявити тонкі помилки, які важко знайти вручну.

### Приклад: Відсутнє очищення Effect

#### Початковий помилковий код:

```js
const serverUrl = 'https://localhost:1234';
const roomId = 'general';

export default function ChatRoom() {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
  }, []);
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

**Проблема**: Цей Effect не має функції очищення.

#### Без Strict Mode

Помилка не очевидна в простих випадках, але стає помітною при додаванні функцій, таких як зміна `roomId` — кількість відкритих з'єднань постійно зростає, спричиняючи проблеми з продуктивністю та мережею.

#### З Strict Mode

Ви одразу бачите проблему. Кількість активних з'єднань показує додаткове з'єднання. Strict Mode запускає додатковий цикл налаштування+очищення для кожного Effect. Оскільки цей Effect не має логіки очищення, він створює додаткове з'єднання, але не знищує його. Це підказує, що відсутня функція очищення.

#### Виправлений код:

```js
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

Тепер ваш Effect "очищує" за собою та знищує застарілі з'єднання.

**Перевага**: Коли ви виправляєте Effect у Strict Mode, ви також виправляєте можливі майбутні продакшн-помилки, такі як витоки з'єднань.

## Виправлення помилок, знайдених повторним запуском колбеків ref у розробці

Strict Mode також може допомогти знайти помилки в колбеках ref.

Кожен колбек `ref` має код налаштування та може мати код очищення. Зазвичай:
- React викликає налаштування, коли елемент створюється (додається до DOM)
- React викликає очищення, коли елемент видаляється (видаляється з DOM)

Коли Strict Mode увімкнено, React запускає **один додатковий цикл налаштування+очищення у розробці для кожного колбека `ref`**. Це допомагає виявити тонкі помилки, які важко знайти вручну.

### Приклад: Відсутнє очищення колбека ref

#### Початковий помилковий код:

```js
<li
  ref={(node) => {
    const list = itemsRef.current;
    const item = {cat: cat, node};
    list.push(item);
    console.log(`Adding cat to the map. Total cats: ${list.length}`);
    if (list.length > 10) {
      console.log('Too many cats in the list!');
    }
    return () => {
      // Немає очищення — це помилка!
    }
  }}
>
  <img src={cat.src} />
</li>
```

**Проблема**: Колбек ref не видаляє елементи зі списку при очищенні. Список постійно зростає, спричиняючи витік пам'яті, що порушує поведінку застосунку.

#### Виправлений код:

```js
return () => {
  list.splice(list.indexOf(item), 1);
  console.log(`Removing cat from the map. Total cats: ${itemsRef.current.length}`);
}
```

Тепер функція очищення правильно видаляє елементи зі списку.

**Перевага**: Коли ви виправляєте колбек у Strict Mode, ви також виправляєте можливі майбутні продакшн-помилки та витоки пам'яті.

## Виправлення попереджень про застарілі API, увімкнених Strict Mode

React попереджає, якщо якийсь компонент всередині дерева `<StrictMode>` використовує один з цих застарілих API:

- Методи життєвого циклу класів `UNSAFE_`, такі як `UNSAFE_componentWillMount`

Ці API переважно використовуються у старих класових компонентах, тому вони рідко з'являються в сучасних застосунках.

---

## Підсумок

**Strict Mode допомагає вам:**
- Знаходити помилки, спричинені нечистим рендерингом, через подвійний рендеринг
- Знаходити помилки, спричинені відсутнім очищенням Effect, через повторний запуск ефектів
- Знаходити помилки, спричинені відсутнім очищенням ref, через повторний запуск колбеків ref
- Ідентифікувати використання застарілих API

**Ключові переваги:**
- Усі перевірки виконуються лише в режимі розробки і не впливають на продакшн
- Допомагає виявляти помилки на ранньому етапі, до того як їх зустрінуть користувачі
- Рекомендовано для всіх нових застосунків
- Може застосовуватися до конкретних частин вашого застосунку
