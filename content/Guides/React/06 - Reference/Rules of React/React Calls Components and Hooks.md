# React викликає компоненти та хуки

## Огляд

React відповідає за рендеринг компонентів та хуків, коли це необхідно для оптимізації користувацького досвіду. Він є декларативним: ви вказуєте React, що рендерити в логіці вашого компонента, і React визначить, як найкраще відобразити це для вашого користувача.

---

## Ніколи не викликайте функції компонентів напряму

Компоненти повинні використовуватися лише в JSX. Не викликайте їх як звичайні функції. React повинен їх викликати.

React повинен вирішувати, коли функція вашого компонента викликається під час рендерингу. У React ви робите це за допомогою JSX.

**✅ Добре: Використовуйте компоненти лише в JSX**
```js
function BlogPost() {
  return <Layout><Article /></Layout>;
}
```

**🔴 Погано: Ніколи не викликайте їх напряму**
```js
function BlogPost() {
  return <Layout>{Article()}</Layout>;
}
```

Якщо компонент містить хуки, легко порушити Rules of Hooks, коли компоненти викликаються напряму в циклі або умовно.

### Переваги надання React контролю над рендерингом

* **Компоненти стають чимось більшим, ніж функції.** React може доповнити їх можливостями, як-от _локальний стан_ через хуки, які прив'язані до ідентичності компонента в дереві.

* **Типи компонентів беруть участь у reconciliation.** Дозволяючи React викликати ваші компоненти, ви також повідомляєте йому більше про концептуальну структуру вашого дерева. Наприклад, коли ви переходите від рендерингу `<Feed>` до сторінки `<Profile>`, React не намагатиметься повторно їх використати.

* **React може покращити ваш користувацький досвід.** Наприклад, він може дозволити браузеру виконати деяку роботу між викликами компонентів, щоб повторний рендеринг великого дерева компонентів не блокував основний потік.

* **Краща історія налагодження.** Якщо компоненти є першокласними сутностями, про які знає бібліотека, ми можемо створювати багаті інструменти розробника для інтроспекції під час розробки.

* **Ефективніший reconciliation.** React може вирішити, які саме компоненти в дереві потребують повторного рендерингу, та пропустити ті, що не потребують. Це робить ваш додаток швидшим та чутливішим.

---

## Ніколи не передавайте хуки як звичайні значення

Хуки повинні викликатися лише всередині компонентів або хуків. Ніколи не передавайте їх як звичайні значення.

Хуки дозволяють доповнити компонент можливостями React. Їх завжди слід викликати як функцію та ніколи не передавати як звичайне значення. Це забезпечує _локальне міркування_, або здатність розробників зрозуміти все, що може робити компонент, дивлячись на цей компонент ізольовано.

Порушення цього правила призведе до того, що React не зможе автоматично оптимізувати ваш компонент.

### Не мутуйте хуки динамічно

Хуки повинні бути якомога "статичнішими". Це означає, що ви не повинні динамічно їх мутувати. Наприклад, не пишіть хуки вищого порядку:

**🔴 Погано: не пишіть хуки вищого порядку**
```js
function ChatInput() {
  const useDataWithLogging = withLogging(useData);
  const data = useDataWithLogging();
}
```

Хуки повинні бути незмінними та не мутованими. Замість динамічної мутації хука створіть статичну версію хука з бажаною функціональністю.

**✅ Добре: Створіть нову версію хука**
```js
function ChatInput() {
  const data = useDataWithLogging();
}

function useDataWithLogging() {
  // ... Створіть нову версію хука та вбудуйте логіку тут
}
```

### Не використовуйте хуки динамічно

Хуки також не повинні використовуватися динамічно. Не робіть dependency injection у компоненті, передаючи хук як значення:

**🔴 Погано: не передавайте хуки як props**
```js
function ChatInput() {
  return <Button useData={useDataWithLogging} />
}
```

Ви завжди повинні вбудовувати виклик хука безпосередньо в компонент та обробляти будь-яку логіку там.

**✅ Добре: Використовуйте хук напряму**
```js
function ChatInput() {
  return <Button />
}

function Button() {
  const data = useDataWithLogging();
}

function useDataWithLogging() {
  // Якщо є умовна логіка для зміни поведінки хука, вона повинна бути вбудована
  // в сам хук
}
```

Таким чином, `<Button />` набагато легше зрозуміти та налагодити. Коли хуки використовуються динамічно, це значно збільшує складність вашого додатку та ускладнює локальне міркування, роблячи вашу команду менш продуктивною в довгостроковій перспективі. Це також полегшує випадкове порушення Rules of Hooks, що хуки не повинні викликатися умовно.

Якщо вам потрібно мокувати компоненти для тестів, краще мокувати сервер, щоб він відповідав заготовленими даними. Якщо можливо, зазвичай також ефективніше тестувати ваш додаток за допомогою end-to-end тестів.
