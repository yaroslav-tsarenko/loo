# Компоненти та хуки повинні бути чистими

## Вступ

Чисті функції виконують лише обчислення і нічого більше. Це робить ваш код легшим для розуміння, налагодження та дозволяє React автоматично правильно оптимізувати ваші компоненти та хуки.

> **Примітка:** Ця сторінка довідки охоплює просунуті теми та вимагає знайомства з концепціями, розглянутими на сторінці "Keeping Components Pure".

---

## Чому чистота має значення?

Чистота є однією з ключових концепцій, що робить React, _React_. Чистий компонент або хук — це такий, що:

- **Ідемпотентний** — Ви завжди отримуєте однаковий результат щоразу, коли запускаєте його з тими самими вхідними даними — props, state, context для компонентів; та аргументами для хуків.
- **Не має побічних ефектів у render** — Код з побічними ефектами повинен виконуватися окремо від рендерингу. Наприклад, як event handler — де користувач взаємодіє з UI та спричиняє його оновлення; або як Effect — який запускається після render.
- **Не мутує нелокальні значення** — Компоненти та хуки ніколи не повинні модифікувати значення, які не були створені локально під час render.

Коли render залишається чистим, React може зрозуміти, як пріоритизувати, які оновлення найважливіші для користувача. Це можливо завдяки чистоті render: оскільки компоненти не мають побічних ефектів у render, React може призупинити рендеринг компонентів, які не так важливо оновлювати, та повернутися до них пізніше, коли це потрібно.

Конкретно, це означає, що логіка рендерингу може виконуватися кілька разів у спосіб, що дозволяє React надавати вашому користувачу приємний досвід. Однак, якщо ваш компонент має невідстежуваний побічний ефект — наприклад, модифікацію значення глобальної змінної під час render — коли React запустить ваш код рендерингу знову, ваші побічні ефекти будуть спрацьовувати у спосіб, що не відповідає вашим очікуванням. Це часто призводить до несподіваних багів, які можуть погіршити досвід ваших користувачів.

### Як React виконує ваш код?

React є декларативним: ви вказуєте React, _що_ рендерити, і React визначить, _як_ найкраще відобразити це для вашого користувача. Для цього React має кілька фаз, під час яких він виконує ваш код.

_Рендеринг_ означає обчислення того, як має виглядати наступна версія вашого UI. Після рендерингу React бере це нове обчислення та порівнює його з обчисленням, використаним для створення попередньої версії вашого UI. Потім React застосовує лише мінімальні зміни до DOM (те, що ваш користувач фактично бачить). Нарешті, Effects запускаються (тобто виконуються, доки не залишиться більше).

#### Як визначити, чи код виконується під час render

Один швидкий евристичний метод — перевірити, де він знаходиться: якщо він написаний на верхньому рівні, є хороший шанс, що він виконується під час render.

```js
function Dropdown() {
  const selectedItems = new Set(); // створено під час render
  // ...
}
```

Event handlers та Effects не виконуються під час render:

```js
function Dropdown() {
  const selectedItems = new Set();
  const onSelect = (item) => {
    // цей код в event handler, тому він виконується лише коли користувач активує це
    selectedItems.add(item);
  }
}
```

```js
function Dropdown() {
  const selectedItems = new Set();
  useEffect(() => {
    // цей код всередині Effect, тому він виконується лише після рендерингу
    logForAnalytics(selectedItems);
  }, [selectedItems]);
}
```

## Компоненти та хуки повинні бути ідемпотентними

Компоненти повинні завжди повертати однаковий вивід відносно їхніх вхідних даних — props, state та context. Це відомо як _ідемпотентність_. Це означає, що ви завжди отримуєте однаковий результат щоразу, коли запускаєте цей фрагмент коду з тими самими вхідними даними.

Це означає, що _весь_ код, який виконується під час render, також повинен бути ідемпотентним для дотримання цього правила. Наприклад, цей рядок коду не є ідемпотентним (а отже, і компонент):

```js
function Clock() {
  const time = new Date(); // 🔴 Погано: завжди повертає різний результат!
  return <span>{time.toLocaleString()}</span>
}
```

`new Date()` не є ідемпотентним, оскільки завжди повертає поточну дату та змінює результат при кожному виклику. Коли ви рендерите вищенаведений компонент, час, відображений на екрані, залишиться зафіксованим на часі рендерингу компонента. Аналогічно, функції на кшталт `Math.random()` також не є ідемпотентними, оскільки повертають різні результати при кожному виклику, навіть коли вхідні дані однакові.

Це не означає, що ви не повинні використовувати неідемпотентні функції на кшталт `new Date()` _взагалі_ — просто уникайте їх використання під час render. У цьому випадку ми можемо _синхронізувати_ останню дату з цим компонентом за допомогою Effect:

```js
import { useState, useEffect } from 'react';

function useTime() {
  // 1. Відстежуємо стан поточної дати. `useState` отримує функцію ініціалізації як
  //    початковий стан. Вона виконується лише один раз при виклику хука, тому лише поточна
  //    дата на момент виклику хука встановлюється першою.
  const [time, setTime] = useState(() => new Date());

  useEffect(() => {
    // 2. Оновлюємо поточну дату щосекунди за допомогою `setInterval`.
    const id = setInterval(() => {
      setTime(new Date()); // ✅ Добре: неідемпотентний код більше не виконується в render
    }, 1000);
    // 3. Повертаємо функцію очищення, щоб не було витоку таймера `setInterval`.
    return () => clearInterval(id);
  }, []);

  return time;
}

export default function Clock() {
  const time = useTime();
  return <span>{time.toLocaleString()}</span>;
}
```

Обгортаючи неідемпотентний виклик `new Date()` в Effect, ми переміщуємо це обчислення за межі рендерингу.

Якщо вам не потрібно синхронізувати зовнішній стан з React, ви також можете розглянути використання event handler, якщо оновлення потрібне лише у відповідь на взаємодію користувача.

## Побічні ефекти повинні виконуватися поза рендером

Побічні ефекти не повинні виконуватися під час render, оскільки React може рендерити компоненти кілька разів для створення найкращого користувацького досвіду.

> **Примітка:** Побічні ефекти — це ширший термін, ніж Effects. Effects конкретно означають код, обгорнутий у `useEffect`, тоді як побічний ефект — це загальний термін для коду, що має будь-який спостережуваний ефект, крім його основного результату — повернення значення.
>
> Побічні ефекти зазвичай записуються всередині event handlers або Effects. Але ніколи під час render.

Хоча render повинен залишатися чистим, побічні ефекти необхідні в якийсь момент для того, щоб ваш додаток робив щось цікаве, наприклад, показував щось на екрані! Ключовий момент цього правила — побічні ефекти не повинні виконуватися під час render, оскільки React може рендерити компоненти кілька разів. У більшості випадків ви використовуватимете event handlers для обробки побічних ефектів. Використання event handler явно вказує React, що цей код не потрібно запускати під час render, зберігаючи render чистим. Якщо ви вичерпали всі варіанти — і лише як останній засіб — ви також можете обробляти побічні ефекти за допомогою `useEffect`.

### Коли допустима мутація?

#### Локальна мутація

Один типовий приклад побічного ефекту — мутація, яка в JavaScript означає зміну значення непримітивного типу. Загалом, хоча мутація не є ідіоматичною в React, _локальна_ мутація цілком прийнятна:

```js
function FriendList({ friends }) {
  const items = []; // ✅ Добре: створено локально
  for (let i = 0; i < friends.length; i++) {
    const friend = friends[i];
    items.push(
      <Friend key={friend.id} friend={friend} />
    ); // ✅ Добре: локальна мутація допустима
  }
  return <section>{items}</section>;
}
```

Немає потреби ускладнювати код для уникнення локальної мутації. `Array.map` також можна використати для стислості, але немає нічого поганого у створенні локального масиву та додаванні елементів під час render.

Хоча виглядає, що ми мутуємо `items`, ключовий момент у тому, що цей код робить це лише _локально_ — мутація не "запам'ятовується" при повторному рендерингу компонента. Іншими словами, `items` існує лише стільки, скільки існує компонент. Оскільки `items` завжди _перестворюється_ щоразу, коли рендериться `<FriendList />`, компонент завжди повертатиме однаковий результат.

З іншого боку, якщо `items` створено за межами компонента, він зберігає попередні значення та пам'ятає зміни:

```js
const items = []; // 🔴 Погано: створено за межами компонента
function FriendList({ friends }) {
  for (let i = 0; i < friends.length; i++) {
    const friend = friends[i];
    items.push(
      <Friend key={friend.id} friend={friend} />
    ); // 🔴 Погано: мутує значення, створене за межами render
  }
  return <section>{items}</section>;
}
```

Коли `<FriendList />` запуститься знову, ми продовжимо додавати `friends` до `items` щоразу, коли компонент запускається, що призведе до кількох дубльованих результатів. Ця версія `<FriendList />` має спостережувані побічні ефекти під час render та **порушує правило**.

#### Лінива ініціалізація

Лінива ініціалізація також допустима, незважаючи на те, що вона не є повністю "чистою":

```js
function ExpenseForm() {
  SuperCalculator.initializeIfNotReady(); // ✅ Добре: якщо не впливає на інші компоненти
  // Продовжити рендеринг...
}
```

#### Зміна DOM

Побічні ефекти, що безпосередньо видимі для користувача, не допускаються в логіці render React компонентів. Іншими словами, просто виклик функції компонента не повинен сам по собі спричиняти зміну на екрані.

```js
function ProductDetailPage({ product }) {
  document.title = product.title; // 🔴 Погано: змінює DOM
}
```

Один спосіб досягти бажаного результату оновлення `document.title` за межами render — синхронізувати компонент з `document` за допомогою Effects.

Поки виклик компонента кілька разів є безпечним і не впливає на рендеринг інших компонентів, React не вимагає, щоб він був 100% чистим у строгому функціональному сенсі. Важливіше те, що компоненти повинні бути ідемпотентними.

## Props та State є незмінними

Props та state компонента є незмінними знімками. Ніколи не мутуйте їх напряму. Натомість передавайте нові props вниз і використовуйте функцію setter з `useState`.

Ви можете думати про значення props та state як знімки, що оновлюються після рендерингу. З цієї причини ви не модифікуєте змінні props або state напряму: натомість передаєте нові props або використовуєте функцію setter, щоб повідомити React, що стан потрібно оновити при наступному рендерингу компонента.

### Не мутуйте Props

Props є незмінними, тому що якщо ви їх мутуєте, додаток створюватиме непослідовний вивід, який може бути важко налагодити, оскільки він може працювати або не працювати залежно від обставин.

```js
function Post({ item }) {
  item.url = new Url(item.url, base); // 🔴 Погано: ніколи не мутуйте props напряму
  return <Link url={item.url}>{item.title}</Link>;
}
```

```js
function Post({ item }) {
  const url = new Url(item.url, base); // ✅ Добре: створіть копію
  return <Link url={url}>{item.title}</Link>;
}
```

### Не мутуйте State

`useState` повертає змінну стану та setter для оновлення цього стану.

```js
const [stateVariable, setter] = useState(0);
```

Замість оновлення змінної стану на місці, нам потрібно оновлювати її за допомогою функції setter, поверненої `useState`. Зміна значень змінної стану не спричиняє оновлення компонента, залишаючи ваших користувачів із застарілим UI. Використання функції setter повідомляє React, що стан змінився, і нам потрібно поставити в чергу повторний рендер для оновлення UI.

```js
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    count = count + 1; // 🔴 Погано: ніколи не мутуйте state напряму
  }

  return (
    <button onClick={handleClick}>
      You pressed me {count} times
    </button>
  );
}
```

```js
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1); // ✅ Добре: використовуйте функцію setter, повернену useState
  }

  return (
    <button onClick={handleClick}>
      You pressed me {count} times
    </button>
  );
}
```

## Повернуті значення та аргументи хуків є незмінними

Після передачі значень у хук ви не повинні їх модифікувати. Як props у JSX, значення стають незмінними при передачі в хук.

```js
function useIconStyle(icon) {
  const theme = useContext(ThemeContext);
  if (icon.enabled) {
    icon.className = computeStyle(icon, theme); // 🔴 Погано: ніколи не мутуйте аргументи хуків напряму
  }
  return icon;
}
```

```js
function useIconStyle(icon) {
  const theme = useContext(ThemeContext);
  const newIcon = { ...icon }; // ✅ Добре: створіть копію
  if (icon.enabled) {
    newIcon.className = computeStyle(icon, theme);
  }
  return newIcon;
}
```

Один важливий принцип у React — _локальне міркування_: здатність зрозуміти, що робить компонент або хук, дивлячись на його код ізольовано. Хуки повинні розглядатися як "чорні ящики" при їх виклику. Наприклад, користувацький хук міг використати свої аргументи як залежності для мемоїзації значень всередині:

```js
function useIconStyle(icon) {
  const theme = useContext(ThemeContext);

  return useMemo(() => {
    const newIcon = { ...icon };
    if (icon.enabled) {
      newIcon.className = computeStyle(icon, theme);
    }
    return newIcon;
  }, [icon, theme]);
}
```

Якщо ви мутуватимете аргументи хука, мемоїзація користувацького хука стане некоректною, тому важливо уникати цього.

```js
style = useIconStyle(icon);         // `style` мемоїзовано на основі `icon`
icon.enabled = false;               // Погано: 🔴 ніколи не мутуйте аргументи хуків напряму
style = useIconStyle(icon);         // повертається раніше мемоїзований результат
```

```js
style = useIconStyle(icon);         // `style` мемоїзовано на основі `icon`
icon = { ...icon, enabled: false }; // Добре: ✅ створіть копію
style = useIconStyle(icon);         // обчислюється нове значення `style`
```

Аналогічно, важливо не модифікувати повернуті значення хуків, оскільки вони можуть бути мемоїзовані.

## Значення є незмінними після передачі в JSX

Не мутуйте значення після того, як вони були використані в JSX. Перемістіть мутацію до створення JSX.

Коли ви використовуєте JSX у виразі, React може завчасно обчислити JSX до того, як компонент закінчить рендеринг. Це означає, що мутація значень після їх передачі в JSX може призвести до застарілого UI, оскільки React не знатиме, що потрібно оновити вивід компонента.

```js
function Page({ colour }) {
  const styles = { colour, size: "large" };
  const header = <Header styles={styles} />;
  styles.size = "small"; // 🔴 Погано: styles вже використано в JSX вище
  const footer = <Footer styles={styles} />;
  return (
    <>
      {header}
      <Content />
      {footer}
    </>
  );
}
```

```js
function Page({ colour }) {
  const headerStyles = { colour, size: "large" };
  const header = <Header styles={headerStyles} />;
  const footerStyles = { colour, size: "small" }; // ✅ Добре: ми створили нове значення
  const footer = <Footer styles={footerStyles} />;
  return (
    <>
      {header}
      <Content />
      {footer}
    </>
  );
}
```
