# incompatible-library

## Огляд

Перевіряє використання бібліотек, несумісних з мемоізацією (ручною або автоматичною).

## Примітка

Ці бібліотеки були розроблені до того, як правила мемоізації React були повністю задокументовані. На той час вони зробили правильний вибір для оптимізації ергономічних способів підтримки належної реактивності компонентів при зміні стану програми. Хоча ці застарілі патерни працювали, з того часу було виявлено, що вони несумісні з програмною моделлю React. Робота з авторами бібліотек для міграції цих бібліотек на патерни, які відповідають Правилам React, продовжується.

## Деталі правила

Деякі бібліотеки використовують патерни, які не підтримуються React. Коли лінтер виявляє використання цих API з [відомого списку](https://github.com/facebook/react/blob/main/compiler/packages/babel-plugin-react-compiler/src/HIR/DefaultModuleTypeProvider.ts), він позначає їх цим правилом. Це означає, що React Compiler може автоматично пропускати компоненти, які використовують ці несумісні API, щоб уникнути поломки вашої програми.

### Приклад: Як мемоізація ламається

```js
// Приклад того, як мемоізація ламається з цими бібліотеками
function Form() {
  const { watch } = useForm();

  // ❌ Це значення ніколи не оновиться, навіть коли поле 'name' зміниться
  const name = useMemo(() => watch('name'), [watch]);

  return <div>Name: {name}</div>; // UI виглядає "замороженим"
}
```

React Compiler автоматично мемоізує значення відповідно до Правил React. Якщо щось ламається з ручним `useMemo`, це також зламає автоматичну оптимізацію компілятора. Це правило допомагає виявити ці проблемні патерни.

## Глибоке занурення: Проектування API, що відповідають Правилам React

Одне питання, яке варто розглянути при проектуванні API бібліотеки або hook, — чи можна безпечно мемоізувати виклик API за допомогою `useMemo`. Якщо ні, то і ручна, і автоматична мемоізація React Compiler зламають код ваших користувачів.

### Проблема внутрішньої мутабельності

Один такий несумісний патерн — "внутрішня мутабельність" (interior mutability). Внутрішня мутабельність — це коли об'єкт або функція зберігає свій власний прихований стан, який змінюється з часом, навіть якщо посилання на нього залишається тим самим. Уявіть це як коробку, яка виглядає однаково зовні, але таємно переставляє свій вміст. React не може визначити, що щось змінилось, тому що він перевіряє лише чи ви дали йому іншу коробку, а не що всередині. Це ламає мемоізацію, оскільки React покладається на те, що зовнішній об'єкт (або функція) змінюється, якщо частина його значення змінилась.

### Рекомендації з проектування

Як загальне правило, при проектуванні React API, подумайте, чи зламає його `useMemo`:

```js
function Component() {
  const { someFunction } = useLibrary();
  // завжди має бути безпечно мемоізувати функції таким чином
  const result = useMemo(() => someFunction(), [someFunction]);
}
```

Замість цього проектуйте API, які повертають іммутабельний стан та використовують явні функції оновлення:

```js
// ✅ Добре: Повертає іммутабельний стан, який змінює посилання при оновленні
function Component() {
  const { field, updateField } = useLibrary();
  // це завжди безпечно мемоізувати
  const greeting = useMemo(() => `Hello, ${field.name}!`, [field.name]);

  return (
    <div>
      <input
        value={field.name}
        onChange={(e) => updateField('name', e.target.value)}
      />
      <p>{greeting}</p>
    </div>
  );
}
```

## Невалідні приклади

Приклади неправильного коду для цього правила:

```js
// ❌ react-hook-form `watch`
function Component() {
  const {watch} = useForm();
  const value = watch('field'); // Внутрішня мутабельність
  return <div>{value}</div>;
}

// ❌ TanStack Table `useReactTable`
function Component({data}) {
  const table = useReactTable({
    data,
    columns,
    getCoreRowModel: getCoreRowModel(),
  });
  // екземпляр table використовує внутрішню мутабельність
  return <Table table={table} />;
}
```

### Застереження: MobX

Патерни MobX, такі як `observer`, також порушують припущення мемоізації, але лінтер поки не виявляє їх. Якщо ви покладаєтесь на MobX і виявляєте, що ваша програма не працює з React Compiler, вам може знадобитися використати директиву `"use no memo"`.

```js
// ❌ MobX `observer`
const Component = observer(() => {
  const [timer] = useState(() => new Timer());
  return <span>Seconds passed: {timer.secondsPassed}</span>;
});
```

## Валідні приклади

Приклади правильного коду для цього правила:

```js
// ✅ Для react-hook-form використовуйте `useWatch`:
function Component() {
  const {register, control} = useForm();
  const watchedValue = useWatch({
    control,
    name: 'field'
  });

  return (
    <>
      <input {...register('field')} />
      <div>Current value: {watchedValue}</div>
    </>
  );
}
```

Деякі інші бібліотеки ще не мають альтернативних API, сумісних з моделлю мемоізації React. Якщо лінтер автоматично не пропускає ваші компоненти або hooks, які викликають ці API, будь ласка, [створіть issue](https://github.com/facebook/react/issues), щоб це можна було додати до лінтера.
