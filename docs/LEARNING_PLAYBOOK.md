# LEARNING PLAYBOOK — як ми вчимо

Цей документ — «конституція» контенту і фіч. Кожна стаття, картка, челендж і екран мають спиратися на перевірені когнітивною наукою методи (Make It Stick, Brown/Roediger/McDaniel; Learning How to Learn, Oakley; дослідження Dunlosky 2013; практики Harvard CS50 та MIT 6.031).

## 1. Принципи

| # | Принцип | Що це | Як реалізовано в апці |
|---|---|---|---|
| 1 | **Retrieval practice** | Пригадування сильніше за перечитування | Картки FSRS, міні-квізи після кожної секції, режим «стрічка» |
| 2 | **Spaced repetition** | Повторення з інтервалами, що ростуть | FSRS-розклад, денна місія завжди починається з due-карток |
| 3 | **Pretesting / prediction** | Спроба відповісти *до* пояснення підвищує засвоєння | Кожна стаття стартує з `🤔 Передбач` — квіз «що виведе код» до теорії |
| 4 | **Interleaving** | Перемішування тем краще за блоки однієї теми | Стрічка і денна місія змішують теми, типи і рівні |
| 5 | **Elaboration** | «Чому?» і «як це пов'язано з…?» | Секції `🔗 Зв'язки`, питання «поясни чому» у картках |
| 6 | **Dual coding** | Слова + зображення | `[!viz]` інтерактивні схеми, ASCII/mermaid-подібні схеми, емодзі-якорі |
| 7 | **Concrete examples** | Абстракція через конкретику | Кожна ідея → мінімальний приклад коду + аналогія з життя |
| 8 | **Worked → faded examples** | Розв'язаний приклад → частково → самостійно | `type: fill` → `type: order` → `[!task]` з автотестами |
| 9 | **Feynman technique** | Поясни простими словами | Блок `🧒 Поясни п'ятирічному` + задача «поясни своїми словами» |
| 10 | **Desirable difficulty** | Зусилля = пам'ять | Підказки відкриваються поступово, рішення — тільки після спроби |
| 11 | **Metacognition** | Знати, що ти знаєш | Самооцінка «знав / важко / не знав», статистика слабких тем |
| 12 | **Chunking** | Малі смислові блоки | Секції по 3–5 хв читання, рілси по 20–40 секунд |
| 13 | **Habit loop** | Тригер → дія → нагорода | Денна місія, серії 🔥, XP, рівні, ліги, бос-тести |

### 2.1 Писати код, а не лише читати

Читання коду створює ілюзію компетентності: «я розумію» ≠ «я напишу». Тому кожен розділ доводить учня до **написання** коду в три сходинки (worked → faded → самостійно, принцип 8):

1. **`type: fill` — заповни пропуски.** Майже готовий код з 2–4 пропусками в ключових місцях (саме те, що розділ пояснює: `let` проти `var`, `await`, `return`, умова виходу з рекурсії). Найменше когнітивне навантаження — фокус на одній ідеї. `· bank` для першого знайомства з темою, поля вводу — для закріплення.
2. **`type: order` — Parsons problem.** Учень складає рішення з перемішаних рядків. Дослідження (Parsons & Haden 2006; Ericson et al. 2017–2022) показують: такі задачі дають порівнянний приріст навичок із написанням чи виправленням коду, але займають помітно менше часу і менше фруструють. 1–2 дистрактори `// ✗` ловлять типові помилки (`var` замість `let`, `return` не на тому рівні, `=` замість `===`). 4–10 шматків, відступи — частина відповіді.
3. **`[!task]` з автотестами — пишемо самі.** Миттєвий об'єктивний фідбек (червоні/зелені тести) замість самооцінки — це retrieval practice + desirable difficulty в чистому вигляді.

Правила для `🛠️ Практика`:

- **Кожна** задача має ` ```js starter ` (сигнатура + `// твій код`) і ` ```js tests `. Задача без тестів — лише для «поясни своїми словами».
- 3–6 тестів: від простого випадку до крайових (порожній ввід, повторний виклик, помилка). Назва тесту — українською і пояснює **поведінку**: `test('не викликає fn, поки йдуть виклики', …)`.
- Таймери тестуй через `vi.useFakeTimers()` + `vi.advanceTimersByTime()`, а не `sleep` — швидко й детерміновано (ліміт усього запуску 3 с).
- Перевіряй, що еталон проходить тести: `pnpm content:check <guide>` проганяє `[!solution]` через `tests`.
- TypeScript-курси пишуть ті самі блоки як ` ```ts starter ` / ` ```ts tests `: типи знімаються перед запуском і **не перевіряються** (ні в браузері, ні в `content:check`). Тож тест «функція повертає `number`» неможливий — перевіряй значення й поведінку; помилку типів показуй у поясненні чи квізі, а не в автотестах.
- У кожному розділі — 2–3 квізи `order` / `fill` у секціях «🔬 Як це працює» (після пояснення) і перед «🛠️ Практика» як розминка.

Синтаксис і повний API тестів — CONTENT_SPEC.md, розділи 4.3.1, 4.3.2 і 4.4.1.

## 3. Стиль

- Мова — українська, терміни англійською в `code` або курсивом там, де так кажуть на співбесідах.
- Тон — розумний друг-сеньйор: коротко, точно, з гумором, без води.
- Емодзі — як навігаційні якорі в заголовках і рілсах (Apple emoji рендеряться нативно на iOS/macOS). Не більше одного на абзац.
- Код — мінімальний, запускається як є, з коментарем очікуваного виводу `// → 3`.
- Факти — точні відповідно до ECMAScript/HTML spec. Не спрощувати до неправди; якщо спрощуємо — кажемо «спрощено».

## 4. Рілс `[!reel]`

```md
> [!reel] 🧩 typeof null — це баг віком 30 років
> У першій реалізації JS значення зберігались з тегом типу, і тег об'єкта був `000`. `null` — нульовий вказівник — теж мав `000`.
>
> ```js
> typeof null // → "object"
> ```
```

Вимоги: заголовок з емодзі ≤ 60 символів, тіло ≤ 280 символів + опційний код ≤ 6 рядків. Один рілс — одна ідея, яку хочеться переслати другу.

## 5. Ілюстрації: `[!viz]` і `[!figure]`

| Блок | Коли | Приклад |
|---|---|---|
| `[!viz]` | **механіка концепції**: що відбувається всередині рушія чи браузера — стек, черги, пам’ять, біти, алгоритм зі специфікації. Читач проходить кроки сам. | `event-loop`, `scope-chain`, `float-precision` |
| `[!figure]` | **реальний інструмент**: як це виглядає в DevTools, редакторі, браузері — щоб завтра повторити руками. Програється сам, як коротке відео. | `devtools-console`, `devtools-network`, `code-editor-run` |

```md
> [!viz] event-loop
> scenario: promise-vs-timeout

> [!figure] devtools-console
> scenario: promise-order · device: auto
>
> Те саме — у справжній консолі Chrome.
```

- Мінімум **2 ілюстрації на розділ**: зазвичай `[!viz]` у «🔬 Як це працює насправді» і `[!figure]` поруч із практикою або пастками. Dual coding працює, коли картинка пояснює текст, а не повторює його.
- Пара «схема → інструмент» найсильніша: спершу механіка (`[!viz] event-loop`), потім де її побачити (`[!figure] devtools-console`).
- Підпис під ілюстрацією — одне речення про те, *на що дивитися*.

Список id і сценаріїв — у CONTENT_SPEC.md, розділи 12 «Візуалізації» і 13 «Сцени».

## 7. Джерела (обов'язково)

Кожне твердження має шлях «копнути глибше». Три рівні посилань:

1. **У кожній картці `[!question]-` і `[!interview]`** — останній рядок відповіді:
   ```md
   > 📚 [[JavaScript - 05. Замикання#🔬 Як це працює насправді|Розділ: замикання]] · [MDN: Closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Closures) · [Spec: Environment Records](https://tc39.es/ecma262/#sec-environment-records)
   ```
   Спершу внутрішній wiki-link на розділ/секцію посібника, де тема розібрана, потім 1–2 зовнішні джерела.
2. **У поясненні `**Пояснення:**` квізу** — опційно одне посилання, якщо пастка неочевидна.
3. **Наприкінці кожного розділу** — секція перед підсумком:
   ```md
   ## 📚 Джерела та що почитати
   - 🟢 [javascript.info — Closure](https://javascript.info/closure) — найкраще пояснення для старту
   - 🟡 [MDN — Closures](https://developer.mozilla.org/…) — довідник з прикладами
   - 🔴 [ECMAScript — 9.1 Environment Records](https://tc39.es/ecma262/#sec-environment-records) — першоджерело
   - 🎥 [Jake Archibald — In The Loop](https://www.youtube.com/watch?v=cCOL7MC4Pl0) — доповідь
   ```
   5–10 пунктів, рівень складності емодзі (🟢 старт, 🟡 глибше, 🔴 специфікація/хардкор, 🎥 відео, 🛠️ інструмент), одне речення «що там знайдеш».

Пріоритет джерел: MDN → ECMAScript / HTML spec → javascript.info → V8 blog / web.dev / Node.js docs → статті визнаних авторів (Jake Archibald, Axel Rauschmayer «Exploring JS», Dan Abramov, Kyle Simpson «YDKJS»). **Кожен URL перевіряй** (`curl -sIL -o /dev/null -w '%{http_code}' URL` → 200); не вигадуй якорі специфікації, яких не бачив.
